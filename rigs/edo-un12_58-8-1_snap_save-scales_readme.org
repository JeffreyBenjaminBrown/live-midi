#+title: The edo-un12 piano rigs -- detune a 12-key keyboard into 58-EDO, MIDI out to Pianoteq

* overview
The player's reference for the *piano-detuning* rig family: a MIDI keyboard plays
into the runtime, the twelve pitch classes are remapped onto an arbitrary EDO
(58 here), and the result leaves as MIDI -- historically into Reaper hosting
Pianoteq. The code makes no sound itself; the receiving synth does.

This one file covers the whole ~edo-un12_*~ family (they differ only in extras):

| rig                                | idiom | layout | extras                          |
| =edo-un12_58-8-1_snap_save-scales= | snap  | 58-8-1 | scale slots (store/recall maps) |
| =edo-un12_58-8-1_snap_recording=   | snap  | 58-8-1 | one recording slot              |
| =edo-un12_58-8-5_snap_recording=   | snap  | 58-8-5 | one recording slot              |
| =edo-un12_31_loose_recording=      | loose | 31-6-1 | one recording slot              |

The runtime behavior (LED priorities, snap/loose idioms, the recording
controls) is documented in [[file:RUNTIME-NOTES.org]] under "Remappable un-12
monome"; this file is the *operating manual* -- how to bring it up and wire it.
Code: =buried/midi_pulse/remap_runtime/= (dispatched by the ~remappable_un12~
piano mapping + a ~remappable_un12_grid~ window; see =buried/midi_pulse/midi_pulse.rs=).

* hardware needed
- ONE or TWO MIDI keyboards (e.g. the Casio, or a pair of identical AK490s),
  plugged into the host. Each shows up as an ALSA device; ~amidi -l~ /
  ~aconnect -l~ list them. With two, each keyboard gets its own Reaper input
  ("58-edo 1" / "58-edo 2") -- see *two keyboards* below.
- Optional: sustain pedal hardware -- either the two M-Audio EX-P expression
  pedals on the DOREMiDi MPC-20 (preferred; needs the host-side bridge
  running), or a KMSS (SoftStep) board. A startup question picks which; see
  *sustain pedals* below. Absent gear gets a red note and a background retry,
  so plugging in later just works.
- ONE monome 256 (16x16). The rigs pin ~select.size = [16, 16]~. Without a grid
  the MIDI transform still starts, but the monome thread panics ("no monome
  found") and you lose the remap UI -- so treat the grid as required.
- The host running Reaper with Pianoteq (or any synth that will interpret the
  multi-channel output; see *the MIDI output encoding* below).

* to run it
** ALL STEPS REQUIRED
*** why
Two steps, BOTH required: start the runtime (this section), then make the
connections (next section). The runtime only *creates* its MIDI ports -- it
connects nothing to them, and no other program does either. A rig that is
"running" (rig summary printed, monome found) but was never connected is
silent and shows no MIDI activity in Reaper; that is the expected symptom of
a skipped step 2, not a broken rig (bitten for real 2026-07-25).

Everything host-side beyond Reaper itself -- the two persistent Reaper
inputs, the a2j export that lets Reaper's device list see them, and the EX-P
pedal bridge -- comes from ONE script, ~./make-2-midi-inputs.sh~ (see
*giving Reaper two MIDI inputs*), run BEFORE Reaper so Reaper's
startup-only device scan finds the ports. The dependency-safe full order:

: ./make-2-midi-inputs.sh (host)  ->  Reaper  ->  the runtime (docker)  ->  connect-midi.sh
** in the container
#+begin_src sh
cargo run --bin midi_pulse -- edo-un12_58-8-1_snap_save-scales
#+end_src
No ~pw-jack~ strictly needed: these rigs have no audio sink (0 ~[[sinks]]~), so
nothing grabs the sound card. (Using ~pw-jack~ anyway is harmless.)

Exit: press Enter -- any line except ~l~, which is the left-keyboard
identification (see *two keyboards*) -- or Ctrl-C. NOTE: stdin EOF also quits --
don't run it with ~< /dev/null~ or backgrounded without a terminal, or it
exits immediately.

On startup it prints the rig summary, "58-EDO remappable un-12 runtime
started", and then (once the grid is found) a ~monome: id=... size=16x16~ line.
It creates two virtual ALSA-seq MIDI port PAIRS (since 2026-07-25; with one
keyboard the second pair just sits idle), visible in ~aconnect -l~ in the
container and, on the host, through PipeWire's Midi-Bridge:
- =edo_un12_piano_monome-in= / =-in-2= -- connect a keyboard INTO each
- =edo_un12_piano_monome-out= / =-out-2= -- connect these into Reaper
Pair 1 is "58-edo 1": the LEFT keyboard, the recorder (recording rigs), and
sustain (EX-P pedal 1, or the SoftStep pad) all live there. Pair 2 is
"58-edo 2", the right keyboard, sustained by EX-P pedal 2.

The sustain-hardware question (see *sustain pedals*) is asked AFTER the ports
are up, and "Press Enter to exit..." prints only once it is answered. An
unanswered question blocks nothing but sustain: step 2 runs fine against a
runtime still sitting at the prompt. (Learned 2026-07-25: the question
originally ran FIRST, and ~connect-midi.sh~ met a portless runtime -- every
MIDI step "not found".)

** on the host (or the container -- the script runs the same from either)
#+begin_src sh
./tools/connect-midi.sh edo-un12_58-8-1_snap_save-scales
#+end_src
This is step 2 of 2 -- without it nothing reaches the rig or Reaper (see the
note at the top of *to run it*). It works from inside the container too
(see *in vs out of Docker* below), so a container shell can do the whole
MIDI bring-up. It reads the rig's ~[midi.input]~ / ~[midi.output]~ ~virtual_name~ values and
connects keyboard(s) -> =...-in=(=-2=), =...-out=(=-2=) -> Reaper, and Reaper's
audio out -> the best built-in output (prefers Headphones; rerun after plugging
or unplugging the 1/8" jack). With ONE keyboard found it behaves as it always
did (keyboard -> =-in=, =-out= -> Reaper's first MIDI input); with TWO it also
wires the second pair (see *two keyboards*). The Reaper MIDI targets prefer
ports named "58-edo 1" / "58-edo 2" when PipeWire can see those names, else
fall back to Reaper's 1st and 2nd MIDI inputs in sorted order -- today that is
"MIDI Input 1" and "MIDI Input 4", because in-Reaper device renames don't
reach PipeWire. Run it AFTER the runtime is up (the virtual ports must exist)
and after Reaper is running.

Preferred: with ~./make-2-midi-inputs.sh~ having run (see *giving Reaper two
MIDI inputs*), this script takes the kernel-thru route instead -- plain
~aconnect~ of the rig outputs into "Midi Through Port-0"/"Port-1" -- and the
Reaper-port hunting above never happens.

Manual equivalents, if the script's guesses are wrong, are in
[[file:RUNTIME-NOTES.org]] "MIDI connection recipes".

** only for the sustain pedals via EX-P pedals
on host, from project root

tools/pedals/bridge.sh

(Already covered if ~./make-2-midi-inputs.sh~ is running -- the setup script
starts the bridge as one of its pieces; run it alone only when you want just
the pedals.)
* two keyboards (since 2026-07-25)
Plug both in (the same model is fine -- they are told apart by ALSA client
number, not name) and run both steps as usual. ~connect-midi.sh~ connects the
first keyboard (client-number order, i.e. plug order) to =-in= and the second
to =-in-2=. Client order says nothing about which keyboard physically sits on
the LEFT, so the runtime owns that decision:

1. In the runtime's terminal, type ~l~ then Enter.
2. It answers "play a note from the left keyboard to identify it".
3. Play any note on the LEFT keyboard. That keyboard becomes "58-edo 1" (and
   the sustain pedal's target); the other becomes "58-edo 2". It prints what
   it decided, e.g. ~left keyboard identified: edo_un12_piano_monome-in-2 ->
   58-edo 1; the other -> 58-edo 2 (routing swapped)~.

The identifying note itself already sounds on 58-edo 1. Type ~l~ again any
time (say, after replugging swapped the client order). Notes HELD through the
swap are safe: a note-off always follows its note-on to whichever output that
note-on used, so nothing sticks. Both keyboards share the ONE live 12->58 map
and monome remap UI -- they are two hands of the same instrument, not two
instruments -- and each stream carries the same channel-per-octave encoding
(see *the MIDI output encoding*), so Reaper needs the same Pianoteq octave
stack on both inputs.

* giving Reaper two MIDI inputs (=make-2-midi-inputs.sh=, since 2026-07-25)
THE fact that shapes this design, established empirically (pw-dump, same
day): Reaper's Linux MIDI-device list shows only ports flagged
~port.physical = True~, and only KERNEL ALSA clients get that flag. Every
user-space port -- the rig runtime's midir ports, rtmidi ports, the pedal
bridge's -- is invisible to Reaper NO MATTER WHAT it is named (a first
attempt at this feature exported nicely-named user-space thrus and Reaper
ignored them all). Two further constraints: Reaper scans devices only at
STARTUP (or "Reset all MIDI devices"), and the runtime's ports die with
every restart -- so Reaper must never read the runtime directly anyway.

The answer to all three at once: KERNEL thru ports -- ~snd-seq-dummy~
loaded with ~ports=2~. "Midi Through Port-0" is 58-edo 1 (the left
keyboard), "Midi Through Port-1" is 58-edo 2. They are physical-flagged (so
Reaper lists them), permanent (so restart order never matters), and true
thrus (whatever the rig writes in, subscribers read out). On the HOST,
FIRST -- before Reaper:

#+begin_src sh
./make-2-midi-inputs.sh
#+end_src

One run does three things and holds the daemons until Ctrl-C (each piece is
skipped if already up, so rerunning is safe):
1. Reloads ~snd-seq-dummy~ with ~ports=2~ (the sudo prompt covers this and
   the bridge). To make it permanent so this step always self-skips, put in
   the NixOS config and reboot:
   : boot.extraModprobeConfig = "options snd-seq-dummy ports=2";
2. Runs ~a2jmidid~, whose a2j-named export of the kernel ports is what
   Reaper's list shows. (Each port exports as "(capture)" and "(playback)"
   -- the same port readable and writable; the input list shows capture.)
3. Runs the MPC-20 pedal bridge (see *sustain pedals*, "the bridge").

Then, ONCE in Reaper (persists): Options > Preferences > MIDI Devices ->
enable inputs *"Midi Through Port-0"* (58-edo 1) and *"Port-1"* (58-edo 2),
and point each Pianoteq octave-stack's tracks at the matching device,
channel-filtered as before. A stale "Port-1 (not found)" entry from an old
setup is THIS device -- it springs back to life once the port exists.

~connect-midi.sh~ closes the loop: when "Midi Through Port-1" exists it
takes the kernel-thru route -- plain ~aconnect~ of
=edo_un12_piano_monome-out= -> Port-0 (and =-out-2= -> Port-1 with two
keyboards) -- and skips its legacy pw-link-to-REAPER step (both routes at
once would double every note). Without Port-1 it falls back to the legacy
route.

* sustain pedals (since 2026-07-25)
On startup -- after its MIDI ports are up, so leaving the prompt unanswered
never blocks the connection step -- the runtime asks:
: sustain pedals: EX-P via the MPC-20 bridge (e) or SoftStep pad 0 (s)? [e]
~e~ -- or bare Enter, or EOF -- picks the EX-P pedals; ~s~ picks the SoftStep;
anything else re-asks. Either way, foot down = an ordinary piano damper
(CC 64 = 127; foot up = 0), sent to EVERY MIDI channel of the target output,
because the encoding spreads octaves over channels and the pedal must hold
them all. Gear missing at startup: a red note prints and discovery retries
every ~2 s, so plugging it in mid-session just works.

** EX-P pedals (the default)
The two M-Audio EX-P expression pedals on the DOREMiDi MPC-20:
- MPC-20 *Pedal 1* (MIDI channel 1) -> *58-edo 1*, the LEFT keyboard.
- MPC-20 *Pedal 2* (MIDI channel 2) -> *58-edo 2*, the right keyboard.
EVERY pedal CC sends a sustain event: raw value at or above 60 sends ON
(ties to on), below 60 sends OFF. No edge detection, no window, no
hysteresis -- deliberately STATELESS, because the bridge's USB stream can
drop messages (observed live 2026-07-25: under an earlier
send-only-on-transitions design, a dropped release sweep froze sustain ON
with the foot off). Resending on every message means the next pedal movement
always resynchronizes Pianoteq, whatever was lost; a stuck sustain can
outlive at most one still pedal. 60 is mid-travel of the pedals' reliable
~1..119 range; the threshold is ~EXP_SUSTAIN_ON_AT~ in
=buried/midi_pulse/remap_runtime/sustain.rs= -- a top-of-file const, like the
travel bounds in =edo_surface/src/expression_pedals.rs=.

*** the bridge (=tools/pedals/bridge.sh=) -- required for EX-P sustain
The MPC-20 never becomes an ALSA MIDI device on Linux: its WCH CH345 chip
ships broken MIDI descriptors and the kernel's CH345 quirk doesn't take on
this composite device, so no port is created -- =amidi -l= / =aconnect -l=
showing nothing is EXPECTED, not the fault. The bridge is the workaround:
=bridge.py= claims the MPC-20's raw USB endpoint and re-emits its MIDI on a
virtual ALSA-seq port named *"MPC-20 pedals"*, which the container shares and
the runtime subscribes to by name -- there is no ~connect-midi.sh~ step for
the pedals. Full story, plus pedal calibration (the MIN trim knob, polarity
switch, the once-clipped 35..127 pedal): [[file:../tools/pedals/README.org]].

Run it on the HOST -- it needs the raw USB device and root, and the container
has neither (~./make-2-midi-inputs.sh~ runs it for you as one of its pieces):
#+begin_src sh
tools/pedals/bridge.sh
#+end_src
- It prompts for the sudo password (root is what detaches the MPC-20's USB
  interface from =snd-usb-audio=) and wraps =bridge.py= in the nix shell that
  has its dependencies (=bridge.nix=: pyusb, python-rtmidi, libusb). Don't
  hand-roll the ~nix-shell --run sudo ...~ line: the wrapper exists to dodge
  two real quoting/PATH traps, documented in its header.
- Leave it running for the whole session; Ctrl-C stops it (and sustain with
  it). It survives unplugging and replugging the MPC-20.
- Start order vs the rig runtime does not matter: the runtime prints its red
  note and retries every ~2 s until the "MPC-20 pedals" port appears.

Verify (container or host alike):
~timeout 10s aseqdump -p 'MPC-20 pedals' 2>&1 | head -20~ and move a pedal --
expect CC 21 lines on channels 0/1 (aseqdump's 0-based names for the MPC-20's
Pedal 1/2). No lines = bridge side broken. Lines here but no sustain =
runtime side: did it print ~sustain pedals: EX-P (...)~ after the startup
question? ~cargo run --bin pedal_monitor~ shows the decoded 0.0..1.0
positions live.

** SoftStep pad 0
With a SoftStep plugged in (either board; matched by "SSCOM" or "SoftStep" in
the port name), the runtime puts it in tether mode and pad printed *0* -- the
RIGHTMOST TOP pad -- becomes the damper for *58-edo 1* only. Standalone mode
is restored on exit, Ctrl-C included.

"Foot on" is a hold WINDOW, not the drumkit's strike detector, with its own
two knobs in =rigs/softstep.toml= (the shared params file; a restart picks up
edits, no rebuild):
- ~sustain_on_sum~ (40): a pad-0 CC whose 4-sensor sum is at least this counts
  as pedal pressure; anything below is no signal at all.
- ~sustain_window_ms~ (150): sustain stays on while the last qualifying signal
  is at most this old. The window lapsing IS the release and the debounce;
  there is deliberately no off threshold. (The tether stream is on-change: a
  resting foot keeps jittering CCs out, a lifted foot goes silent. If a very
  still foot ever drops sustain early, raise ~sustain_window_ms~ -- or use the
  EX-P pedals, whose absolute positions have no such failure mode.)

* robustness of the connection script
~connect-midi.sh~ never dies half-way: every step runs even when an earlier one
failed, each failed step prints WHY it failed and the exact command to make
that connection by hand, and the script ends with a summary of what did not
connect (exit 1) or ~Done!~ (exit 0). Concretely:

- *No keyboard found* (or the runtime's =...-in= port missing because the rig
  isn't running): a warning names which end is missing; the MIDI-to-Reaper and
  audio steps still run. Manual fallback:
  ~aconnect <keyboard-client>:0 <rig-client>:0~ (client numbers from
  ~aconnect -l~).
- *Several possible keyboards*: they are listed and none is guessed; connect
  the right one by hand as above.
- *Reaper not running* (MIDI or audio link fails): the failing ~pw-link~
  command is printed verbatim so you can rerun it once Reaper is up -- or just
  rerun the whole script; connections that already exist are kept
  ("Already connected"), so rerunning is always safe and idempotent.
- *Neither Headphones nor Speaker sink present*: the available sinks are
  listed; pick one and ~pw-link "REAPER:out1" <sink>:playback_FL~ (and ~out2~
  -> ~playback_FR~). Rerun the script after plugging/unplugging the 1/8" jack
  -- it moves Reaper's audio to the currently active sink.

The full by-hand procedure -- every link, in shell AND QJackCtl, each with its
own verification -- is the *manual connection* section below.

* manual connection (worst comes to worst)
If ~connect-midi.sh~ can't do it, here is every link by hand, with a way to
verify each. Every SHELL command here works from the host AND from inside the
container alike -- see *in vs out of Docker* at the end of this section; only
the GUI programs are host-only. The chain, in signal order:

#+begin_example
keyboard --(1: ALSA seq)--> edo_un12_piano_monome-in
  [rig transform]
edo_un12_piano_monome-out --(2: PipeWire MIDI)--> REAPER:MIDI Input 1
  [Pianoteq inside Reaper]
REAPER:out1/out2 --(3: PipeWire audio)--> the active sink
#+end_example

Ports only exist while their programs run, so first: start the rig runtime
(container) and Reaper (host). Step 0, confirm the rig's ports exist:
~aconnect -l | grep edo_un12~ -- nothing means the runtime isn't up (or died).

In QJackCtl's Graph view (per the repo README's color convention): ALSA-seq
MIDI ports are *purple*, JACK/PipeWire MIDI ports are *red*, audio ports are
the remaining (non-MIDI) kind. A made connection is a visible edge between
ports; that verifies the LINK exists, the per-link checks below verify data
actually FLOWS.

** link 1: keyboard -> rig input (ALSA sequencer)
- Make, shell: find both client numbers in ~aconnect -l~ (the keyboard is a
  ~[type=kernel]~ client; the rig is =edo_un12_piano_monome-in=), then
  ~aconnect <keyboard>:0 <rig-in>:0~ (sender first, receiver second).
- Make, QJackCtl: Graph view, purple ports -- drag the keyboard's output port
  onto =edo_un12_piano_monome-in:in=.
- Verify the link: ~aconnect -l~ -- the keyboard's port now shows
  ~Connecting To: <rig-in>:0~.
- Verify keys flow at all (independent of the rig):
  ~timeout 10s aseqdump -p <keyboard-client>:0 2>&1 | head -20~ and press keys
  -- note-on/off lines should appear. (Always aseqdump with timeout+head, per
  the repo README pitfall; never read the raw =/dev/midi*= device, that
  blocks. aseqdump is an extra subscriber, so it does NOT steal events from
  the rig.)
- Verify the rig receives: press a key and watch the rig's terminal -- every
  note prints ~note-on: input <60, 0> -> output (5, 28) [kb 1 -> 58-edo 1]~
  (input note, pitch class -> output channel 1-based, note; the suffix names
  the keyboard port it came in on and the 58-edo stream it left on). No line =
  link 1 broken.

** link 2: rig output -> Reaper MIDI in (PipeWire)
- Make, shell:
  ~pw-link "Midi-Bridge:edo_un12_piano_monome-out:(capture_0) out" "REAPER:MIDI Input 1"~
  If the names have drifted, list live ports: ~pw-link -o | grep -i midi~
  (sources) and ~pw-link -i | grep -i reaper~ (destinations). Second keyboard:
  the same shape with =...-out-2= and the 58-edo 2 Reaper port.
- Make, QJackCtl: Graph view, red ports -- drag the
  =edo_un12_piano_monome-out= port (under the *Midi-Bridge* node) onto
  REAPER's *MIDI Input 1*.
- Verify the link: ~pw-link -l~ -- under the Midi-Bridge source port you
  should see ~|-> REAPER:MIDI Input 1~.
- Verify the rig emits (independent of Reaper):
  ~timeout 10s aseqdump -p edo_un12_piano_monome-out 2>&1 | head -20~, press a
  key -- expect the REMAPPED events (middle C: channel 4 in aseqdump's 0-based
  display, note 28).
- Verify Reaper receives: record-arm the Pianoteq track with its input set to
  All MIDI / that channel -- its input meter should flick on each key press.

** link 3: Reaper -> audio out (PipeWire)
- Make, shell: list the current sinks -- they change when the 1/8" jack is
  (un)plugged: ~pw-link -i | grep 'sink:playback'~. Then
  ~pw-link "REAPER:out1" "<sink>:playback_FL"~ and
  ~pw-link "REAPER:out2" "<sink>:playback_FR"~.
- Make, QJackCtl: Graph view -- drag REAPER's *out1*/*out2* audio ports onto
  the sink node's *playback_FL*/*playback_FR*.
- Verify the link: ~pw-link -l~ -- REAPER:out1 shows ~|-> <sink>:playback_FL~
  (and out2 -> FR).
- Verify audio flows: play a key (or any item in Reaper) -- Reaper's master
  meter should move AND you should hear it. Meter moving but silence = wrong
  sink (jack plugged/unplugged since linking); relist the sinks and relink, or
  just rerun ~./tools/connect-midi.sh <rig>~, which moves Reaper to the
  currently active sink.

** whole-chain check (10 seconds)
Press middle C once and look at three places: the rig terminal prints
~note-on: input <60, 0> -> output (5, 28) [kb 1 -> 58-edo 1]~ (links 0-1
good), the Reaper track
meter flicks (link 2 good), and you hear a note (link 3 + Pianoteq good). The
first place that stays quiet names the broken link.

** in vs out of Docker
There is only ONE ALSA-sequencer graph and ONE PipeWire graph, and both sides
see and can edit them: the container runs with ~--network host~, shares
=/dev/snd= (which carries the kernel seq interface), and bind-mounts the
host's PipeWire socket. Consequences, verified from inside the container
2026-07-23 (listing, creating, and deleting both an ~aconnect~ connection and
a ~pw-link~ link):

- *Works identically in and out*: every shell command in this section --
  ~aconnect~ (list/connect/disconnect), ~aseqdump~, ~aplaymidi~, ~amidi~,
  ~pw-link~ (list/link/unlink, including the sink listing) -- plus
  ~./tools/connect-midi.sh~ itself, which uses only those tools. It is
  documented as a host script, but it runs the same from the container.
- *Host only*: the GUIs -- QJackCtl, Reaper, and Pianoteq inside it are not
  installed in the container -- and physically plugging hardware in.
- *Container only* (in practice): the rig runtime (~cargo run~) and therefore
  the terminal with the note-on trace that link 1's verification watches.

So if you are already in a container shell, connect and verify from there;
you only need a host shell (or the QJackCtl window) for Reaper itself.

* the MIDI output encoding (what Reaper/Pianoteq must expect)
Reference values (hardcoded in ~remap_runtime.rs~ as ~LOWEST_C = 24~,
~MIN_CHANNEL_OUT = 1~, ~MIN_NOTE_OUT = 28~ -- the rig's ~lowest_note~ /
~[midi.output]~ ~min_channel~ / ~min_note~ carry the same values but the un-12
runtime does NOT read the latter two, nor the rig's ~virtual_name~ strings:
port names are hardcoded to =edo_un12_piano_monome-in/-out= plus the second
keyboard's =-in-2/-out-2=. Don't rename them in the rig or ~connect-midi.sh~
-- which DOES read the rig, deriving the =-2= names from the same values --
will look for ports that don't exist).

A keyboard note maps to an absolute EDO step: its pitch class goes through the
current 12->58 map (plus the tracked signed lift, so remaps move by the short
way around the ring), and its octave above note 24 supplies whole octaves.
Then:

#+begin_example
nibble = 1 + step div 58    (one MIDI channel per octave; this is the RAW
                             status-byte channel nibble, 0-based)
note   = 28 + step mod 58   (notes 28..85 = the 58 steps)
#+end_example

*Channel numbering -- read this twice.* The formula's channel is the raw wire
nibble (what ~aseqdump~ prints). Reaper, Pianoteq, and the runtime's own
note-on terminal trace all number channels 1..16, i.e. *nibble + 1*. Verified
example: keyboard note 60 (middle C, initial "even" map, C -> step 0) comes
out as nibble 4 = ~aseqdump~ "channel 4" = *channel 5 in Reaper* (and the
runtime echoes ~output (5, 28)~).

So the receiving side must treat a note ~n~ on wire nibble ~c~ (= Reaper
channel ~c + 1~) as frequency

#+begin_example
f = f_ref * 2 ^ ( (c - 1) + (n - 28)/58 )      c = wire nibble (aseqdump)
  = f_ref * 2 ^ ( (R - 2) + (n - 28)/58 )      R = Reaper/Pianoteq channel 1..16
#+end_example

where f_ref is whatever you tune keyboard-C1's image to (the rig's
~fundamental_hz = 80~ is only used by audio-sink rigs; the MIDI side leaves the
reference to the receiver). In practice that means Pianoteq loads a 58-EDO
scala tuning with its keyboard mapping anchored so note 28 = the reference
pitch, and the octave offset is applied per channel -- e.g. one Pianoteq/track
per used channel in Reaper, each transposed a whole octave from the last, all
fed from the same input filtered by channel.

Range facts (all verified in the code, not just on paper):
- An 88-key keyboard (bottom A0 = note 21) spans wire nibbles 0..8 = Reaper
  channels 1..9. Keys below note 24 are handled correctly (signed math with
  euclidean div/mod): A0 comes out one octave down on nibble 0, not garbage.
- Remapping can push a note across a channel boundary (a downward-lifted
  bottom-octave pitch lands on nibble 0); the receiver needs those channels
  wired, or those notes are silently missing.
- A step whose channel would leave 0..15 is silently dropped by the transform
  (guarded, no crash).

* the monome UI (quick recap; details in RUNTIME-NOTES.org)
- Row 0, x 0..11: the *preimage row* -- the twelve piano pitch classes C..B.
- Below it: the *EDO map*, cell (x,y) = step ~8x + 1y mod 58~ (the "8-1" in the
  rig name; the 58-8-5 rig uses ~y_step = 5~). Lit cells are the current images
  of the twelve pitch classes.
- Bottom-right (15,15): *undo* -- reverts the last remap (or scale recall).
- *snap idiom*: tap a dark cell and the nearest image (distance in the EDO
  ring) moves there.

** save-scales rig only: scale slots
- (12..15, 0..3): a 4x4 grid of *scale slots*, each holding a full 12->58 map.
- (15,4) *store*: press it (it arms; press again to disarm), then press a slot
  to write the current map there. Storing never highlights the slot.
- (14,4) *empty*: same arm-then-slot gesture; empties the slot.
- A bare slot press *recalls* its map -- the whole 12-value map is imposed as
  ONE undoable move, and the slot lights solid as "where you last jumped"
  (the highlight persists even after you edit away from it). Empty slots are
  inert. Arming store disarms empty and vice versa.
- LED legend (2026-07-23): an *empty* slot and an *unarmed* arm button flash
  slow (100 ms on / 100 off), so they are visible even on the old monobright
  256. A *full but inactive* slot is dim -- native dim on a varibright grid,
  faked on the old monome by a fast low-duty flicker (15 ms on / 45 off). The
  *active* (last recalled) slot and an *armed* button are solid full; the
  active slot STAYS solid if you then edit the live map away from it.

** recording rigs only
Controls at (13..15, 0..2): start/stop/loop, arm/erase-ons/end-all, RSCM.
Full semantics in [[file:RUNTIME-NOTES.org]] "Remappable un-12 monome".

- The ~port.physical~ discovery (2026-07-25, later the same day; the reason
  the kernel-thru design exists): a first version of the setup used
  user-space rtmidi thrus named "58-edo 1"/"58-edo 2". Everything on the
  graph side verified live -- the thru clients existed, forwarded injected
  notes end-to-end, and a2jmidid exported them -- yet Reaper's device list
  showed the a2j "Midi Through" port and NOT the identically-shaped 58-edo
  ports. ~pw-dump~ found the one difference: the kernel client's ports carry
  ~port.physical = True~ / ~port.terminal = True~; the user-space ports have
  no such flags. Conclusion (fits every observation all day): Reaper lists
  only physical-flagged ports. Hence snd-seq-dummy ports=2.
