* MIDI, ALSA & the SoftStep (KMSS)  (42)
- [[file:README.org::To read MIDI data without freezing][Reading raw MIDI directly blocks/freezes]]
  Reading raw binary data directly from a MIDI device blocks indefinitely and freezes.  /Fix:/ Use aseqdump with a timeout and head, e.g. `timeout 10s aseqdump -p 20:0 | head -20`; list devices with aconnect -l / amidi -l.
- [[file:TODO/concurrent-drums.org::the short answer (current best hypothesis)][Two drum pads won't fire near-simultaneously (device sends one Program Change)]]
  On the KMSS drumkit, striking two different pedals simultaneously (or nearly so) produces only ONE drum hit; the loss is upstream of our code because the SoftStep's standalone Program-Change preset behaves as a monophonic key-priority selector and emits a single PC for a near-coincident two-pad press. No code fix can recover a MIDI message the device never sent.  /Fix:/ Capture the truth with aseqdump -p 20:0 (or MIDI_PULSE_TRACE=1); if only one PC leaves the device, try the other 12 on-device presets (free, decode is preset-independent as pedal = program % 10), or reprogram to a per-pad Note-On preset / tether mode (both need the currently-blocked host-side send path).
- [[file:TODO/concurrent-drums.org::coalesced two PCs into one buffer][MIDI callback that only accepts a length-2 buffer drops coalesced Program Changes]]
  The callback originally accepted only a length-2 buffer (len()==2 && status==0xC0), so if a backend ever coalesced two PCs into one buffer (C0 05 C0 07, or running-status C0 05 07) BOTH pad hits were silently dropped.  /Fix:/ collect_program_changes now walks the whole buffer and extracts every Program Change including running status; the callback loops over all of them so a coalesced buffer fires both pads.
- [[file:TODO/concurrent-drums.org::what is NOT worth doing][Don't lower/remove debounce_ms to fix concurrency — it's per-pad]]
  It's tempting to blame the 50 ms debounce for the dropped simultaneous hit, but Debouncer keys on the pedal and only gates repeats of the SAME pad; lowering/removing it cannot help two different pedals and just re-enables same-pad bounce.  /Fix:/ Leave debounce_ms at 50 ms; it only stops same-pad bounce and never gates two distinct pedals.
- [[file:TODO/record/plan.org::MIDI output ownership][Live+playback notes on one output note need a source-aware gate (avoid premature note-offs)]]
  When a live piano note and a playback note map to the same output channel/note, naive sends emit duplicate note-ons and a premature note-off when only one source releases, cutting the still-held other source.  /Fix:/ An output gate tracks active sources per output note: send note-on only for the first source, record extra sources without re-sending, and send note-off only when no sources remain.
- [[file:code/python/softstep/capture.py::block-buffers stdout when piped][amidi block-buffers stdout when piped; wrap in stdbuf -oL or live readings never reach the log]]
  When amidi's stdout is piped (not a TTY) it block-buffers, so live MIDI readings would not reach the reader/log until a large buffer fills.  /Fix:/ Launch it as `stdbuf -oL amidi ...` to force line-flushing so each line is emitted immediately.
- [[file:code/python/softstep/echo.py::send_signal(signal.SIGKILL)][aseqdump ignores SIGTERM - SIGKILL it or it lingers holding the port]]
  aseqdump ignores SIGTERM, so proc.terminate() will not stop the subprocess, leaving it running and holding the ALSA port.  /Fix:/ Send SIGKILL on exit (proc.send_signal(signal.SIGKILL)).
- [[file:code/python/softstep/ss.py::The ALSA *rawmidi* path WORKS][SoftStep ignores the ALSA sequencer (aseqsend); only rawmidi (amidi) reaches it]]
  Sending to the SoftStep through the ALSA *sequencer* (aseqsend) silently does nothing - the device ignores it, which led earlier write-ups to wrongly conclude 'we can't send to the device.'  /Fix:/ Use the ALSA *rawmidi* path instead: `amidi -p hw:1,0,0` reaches the device's USB-MIDI IN (proven by a firmware-query reply and a visible standalone<->tether mode switch).   It is easy to fear that toggling standalone<->tether mode could brick the device.  /Fix:/ Mode switching is REVERSIBLE and does not touch firmware, so it cannot brick the device; only an interrupted firmware *flash* can, and this code never flashes.
- [[file:code/python/softstep/ss.py::transiently get EBUSY][amidi -d sensor reader holds the rawmidi node, so the next send transiently EBUSYs]]
  After you terminate the `amidi -d` sensor reader, the rawmidi node stays held for a moment, so an immediately following send gets EBUSY ('busy') and fails.  /Fix:/ send() retries on a busy port: it sleeps 0.25s and retries (up to 8 times) whenever stderr/stdout contains 'busy'.

- [[file:code/rust/midi_pulse/drumkit_runtime/decode.rs::const ON_SUM][Soft foot presses are dropped if they never cross the onset threshold]]

  The device scans its sensors only ~every 10 ms (fixed in firmware).   A hard floor sharpens the attack (peak ~10 ms) while a soft/springy surface (carpet) slows and scatters it (peak lags 20 ms+), so an ATTACK window tuned on one surface misreads velocity on another.  /Fix:/ Re-check / re-tune the ATTACK window whenever you change the playing surface.
- [[file:learnings/keith-mcmillen-softstep.org::The knobs][Drumkit velocity tuning knobs (symptom -> fix)]]
  Miscalibrated decode knobs cause specific failures: hard hits come out weak/dead (ATTACK too short), dynamics feel flat (VELOCITY_DB_RANGE too small), everything maxes out with no headroom (VELOCITY_FULL_SCALE too low), or double/false triggers and stuck non-retriggering pads (ON_SUM/OFF_SUM thresholds).  /Fix:/ Per the decode.rs table: raise ATTACK 1-2 ms if hard hits are weak (lower if laggy); raise VELOCITY_DB_RANGE for more spread; raise VELOCITY_FULL_SCALE toward 508 for headroom; raise ON_SUM to stop double-triggers, lower OFF_SUM if a pad won't retrigger. - [[file:TODO/DONE/monome-looper/5_critique.org::Driving NoteSink under the LooperState lock risks priority inversion / deadlock][Driving NoteSink under the LooperState lock risks realtime deadlock / priority inversion]]
  The cpal callback locks the voices Mutex every audio block on the realtime thread; if the sink is called while LooperState is held, a lock-order inversion across {LooperState, voices} can deadlock and the realtime thread can stall behind grid LED I/O, causing audio dropouts. The v1 plan named only one mutex and omitted the audio-thread-owned voices lock.  /Fix:/ Name voices as the innermost lock, owned by the realtime thread; compute note events under LooperState, DROP it, then drive the sink acquiring ONLY voices — never nest voices under LooperState.

- [[file:TODO/DONE/timbre-manip/2_discussion.org::will likely wire it backwards][AM 'amplitude' controls the wave's least value — easy to wire the depth backwards]]

- [[file:TODO/DONE/timbre-manip/2_discussion.org::Iterating sine does NOT approach a square][Iterating sine does NOT approach a square wave]]

  Per-note timbres mean many voices sum, and the mixer hard-clips at ±0.95, so a volume row that boosts above unity invites clipping.  /Fix:/ Anchor the top cell at unity (today's sink amplitude 0.15) and only attenuate below it; never boost above unity.
- [[file:TODO/loop-timbre-lag.org::Editing never touches ringing voices][Editing a loop note's stored timbre never changes the ringing voice]]

  Group-transpose duplicates voices per fingered pitch; if the count re-bakes off the growing selection on each press it compounds (2 notes x 3 fingers -> 6 -> 18) instead of the intended 2->6.  /Fix:/ Bake each held chord once off the ORIGINAL selection snapshot so N presses over M notes yield N*M, not compounding; enforce in the gesture handler.
- [[file:TODO/DONE/monome-looper/5_critique.org::is_looper_config must dispatch BEFORE is_monome_sawwave_config][is_looper_config must dispatch BEFORE is_monome_sawwave_config]]
  The looper config (edo_note_grid + cpal_sawwave sink) is a superset of the is_monome_sawwave_config predicate; in the first-match if/else dispatch chain, appending the looper arm after the sawwave arm silently routes the looper into sawwave_runtime, which then chokes on the unknown loop windows.  /Fix:/ Insert the is_looper_config() arm ABOVE the sawwave branch, keyed on the looper-only LoopDisplay kind; note dispatch order is load-bearing.
- [[file:TODO/DONE/monome-looper/5_critique.org::double the lock-held-during-IO pattern][Holding the shared lock across UDP LED bursts serializes both grids and the playback thread]]
  The copied model holds state/sounding/recorder locks across a full UDP LED burst (up to 256 blocking send_led_level_set per repaint); with two grids diffing 16x16 against one shared state, each grid's render holds the global lock for its entire UDP burst, blocking the other grid's render and the 1 ms playback thread every tick.  /Fix:/ Each grid thread computes the LED level vector under the lock, drops the lock, then runs its per-cell rendered_cols diff + UDP sends unlocked; memoize the per-grid window/behavior list once at thread start rather than rebuilding it per tick.
- [[file:TODO/DONE/monome-looper/5_critique.org::OutputGate is the wrong thing to retarget][Sawwave voice engine is cell-keyed, not pitch-keyed — OutputGate is the wrong thing to retarget]]
  The saw engine keys voices by VoiceSource::Fingered{xy:cell} spawned from the pressed cell; there is no note->voice index and loop playback has only a stored pitch with no cell, so a pitch-addressed note_on/note_off sink can't map a note_off back to an xy-keyed voice. OutputGate parses MIDI bytes and ref-counts by OutputNote{channel,note}, none of which exists in the audio-only world.  /Fix:/ Build a thin saw NoteSink keyed by pitch/step with its own per-pitch source-set ref-count (reusing only OutputGate's ref-count PATTERN, not its MIDI types), used directly by both the edo key handler and the playback stepping fn.
- [[file:TODO/DONE/monome-looper/5_critique.org::rounds up to == duration silently][Boundary-quantize that rounds up to == duration silently deletes the event]]
  normalize_events drops any event with elapsed >= duration, so a boundary quantization that rounds an event forward to exactly == duration silently deletes it instead of snapping it to the next pass.  /Fix:/ Snap a forward-quantized event to elapsed = Duration::ZERO (next-pass start), never to == duration.
- [[file:TODO/DONE/monome-looper/5_critique.org::flips the timestamp source to wrapped-phase mid-record][current_record_elapsed returns wrapped playback phase and can corrupt recorded times]]
  current_record_elapsed prefers the WRAPPED playback phase when self.playback is true; in a multi-slot model where the recorded slot shares the sounding slot's playback flag, the timestamp source flips to wrapped-phase mid-record and corrupts recorded times.  /Fix:/ Derive record timestamps for the active slot from that slot's own recording_start (never a playback-wrapped phase); the slot being recorded must not share the sounding slot's playback flag.
- [[file:TODO/DONE/pitch-accretion/dialog.org::PITFALL: We must identify the x-y origin][Pitch alone can't identify a fingered voice — enharmonic keys share a pitch]]
  Distinct key pairs (x,y) can map to the same EDO pitch, so keying/looking up a fingered voice by pitch conflates two physical presses.  /Fix:/ Preserve the x-y origin as the voice source (VoiceSource::Fingered{xy}) and permit two voices to share a pitch (don't coordinate their phases); accretion voices key by pitch (VoiceSource::Accreted{pitch}).
- [[file:TODO/DONE/pitch-accretion/dialog.org::why I'd push back on a single Set][Don't store voices in a HashSet<Voice> — mutable audio state can't be Hash+Eq]]
  A HashSet<Voice> forces Voice to be Hash+Eq, but voices carry mutable audio state (phase, env, target volume) you'd be hashing, and a HashSet isn't ergonomic for update-in-place in a tight render loop.  /Fix:/ Keep the sum-type design but use HashMap<VoiceSource, VoiceState> (O(1) keyed access for release-transform and 'does an accretion voice for P exist?'), iterating .values_mut() in the render loop.

* Process & parallel dev  (8)
- [[file:TODO/DONE/monome-looper/5_critique.org::No error/teardown story for the two-grid runtime][Two-grid runtime has no error/teardown story — a single-grid failure leaves a zombie]]
  remap_runtime panics on startup failure (UDP bind, device discovery) and only continues on recv errors; with two required grids each on its own thread, one thread panicking while the other runs leaves stale LEDs on the survivor and a live audio stream (a zombie).  /Fix:/ Add a pre-flight that requires >=2 distinct unclaimed grids and returns a clean Err before spawning any thread; on a fatal error/panic in either thread set STOP_REQUESTED, join both, blank BOTH grids, and drop the cpal stream so the process exits fully dark (implemented via a StopOnExit Drop guard).
- [[file:TODO/concurrent-drums.org::ignores SIGTERM; exit with Ctrl-C][aseqdump ignores SIGTERM — kill -9 if stuck]]
  aseqdump ignores SIGTERM, so a normal kill/terminate leaves it running while you wait to capture two-pad stomps.  /Fix:/ Exit with Ctrl-C, or kill -9 if it is stuck.
- [[file:code/rust/midi_pulse/drumkit_runtime/mod.rs::Arm Ctrl-C / SIGTERM restoration FIRST][Arm signal restoration before any audio/MIDI thread spawns]]
  If signal blocking is set up after audio/MIDI threads spawn, those threads don't inherit the block, and a stray signal can leave the device stuck in tether mode.  /Fix:/ Call `tether::arm()` first, before spawning any audio or MIDI thread, so the signal mask is inherited process-wide; restoration is armed only once tether mode is actually entered.
- [[file:code/rust/midi_pulse/monome.rs::which would race other tests running in the same process][Don't set the process-wide detector-port env var in tests; it races concurrent tests]]
  Pointing discovery at a mock by setting the process-wide MIDI_PULSE_DETECTOR_PORT env var races other tests running in the same process.  /Fix:/ Use `discover_devices_via(sock, listen_port, detector_port)` to pass the detector port explicitly instead of mutating the shared env var.
- [[file:how-to-parallelize-dev.org::or host tools break][Create worktrees with --relative-paths or host tools break]]
  The same tree is /home/ubuntu in the container but /home/jeff/code/midi on the host; absolute .git worktree pointers break host git/magit.  /Fix:/ Always create worktrees with --relative-paths (worktree.useRelativePaths=true, the default here) so they resolve from both sides.
- [[file:how-to-parallelize-dev.org::Shared memory dir][Two Claudes can clobber shared MEMORY.md]]
  Claude's memory lives in ~/.claude, shared across all worktrees, so two Claudes writing MEMORY.md at once can clobber each other and lose lines.
- [[file:how-to-parallelize-dev.org::Avoid =cp -r= of the home dir][Don't cp -r the home dir to clone]]
  cp -r of the home dir drags along target/ (large), .cache, .ssh, and the editor lock.  /Fix:/ Use git clone (only tracked files), placed outside the repo tree; if you must hand-copy, rsync -a --exclude target/ from a clean checkout.
- [[file:learnings/keith-mcmillen-softstep.org::fully-buffered stdout][aseqdump ignores SIGTERM and fully buffers its banner]]
  'timeout 4s aseqdump ...' hangs because aseqdump ignores SIGTERM; and because its banner is fully-buffered stdout, a SIGKILL loses captured output.  /Fix:/ Kill it with 'timeout -s KILL' or 'kill -9'; when capturing to a file wrap it with 'stdbuf -oL' to line-buffer.
