* DONE the model: a chord is a bag of voice snapshots, not a pitch set
This shapes everything downstream, so stating it explicitly. The current
stored reasons live in =RingStore= (=surfaces_runtime/ring.rs=) as per-grid
*pitch sets* -- a pitch is sustained or not. A chord slot cannot work that
way: each stored voice carries its own amplitude, timbre, and factored-pulse
rate, and two slots (or two recalls) may contain the same pitch. So a slot
stores a =Vec= of voice snapshots (pitch + amplitude + timbre + pulse rate),
and a *recalled* chord spawns voices tagged with a chord reason -- per-voice,
not per-pitch. The chord reason will NOT be a third variant crammed into
=RingStore='s pitch sets; it lives with the voices. (=remove_reason='s
"anything else still holding this up?" logic still gets consulted -- a chord
voice's pitch can additionally be fingered/sustained -- see the collision
TODO below.)

The earlier implementation you remember is the sawwave runtime's chord
machinery (=sawwave/state.rs=: =chords=, =emitting_chord=,
=VoiceSource::Accreted { chord, .. }=). It is per-pitch and built around an
"emitting chord" concept; v2 shares neither. I'd leave it entirely untouched
-- v2 is new code in =surfaces_runtime=.

* DONE a save captures fingered + sustained + chord voices -- not release tails
"Every voice that monome is currently sounding" read literally would also

* ONGOING amplitude: what exactly is stored, and does the pedal reach a recalled voice LATER?
A live voice's loudness is a product: timbre slot gain x the EX-P pedal gain
x the envelope (attack / pluck decay / release), all per-voice in the synth.
I read the vision as: store the *settled product* of timbre gain and pedal
gain at save time (envelope excluded -- see the re-strike item below), and on
recall, spawn at exactly that loudness even if the pedal now sits somewhere
else. Good so far.

The unspecified half: what happens when you move the pedal *after* recall?
Options:

1. Chord voices are permanently exempt from the pedal. Literal reading. But
   then the volume pedal no longer controls part of what the grid is
   sounding, and a recalled chord can never be faded -- only killed by the
   pedal 1 clear. For a "backing layer" use that might even be the point,
   but it makes the EX-P lie as a grid volume.
2. Pedal pickup (my recommendation): a recalled voice keeps its baked-in
   pedal gain until the pedal next *moves*; the first CC after recall makes
   chord voices adopt the live pedal like every other voice, through the
   existing ~20 ms per-voice slew (so the jump is a quick fade, not a
   click). "Ignores the pedal's current state" stays true at recall --
   moving the pedal is an explicit act, and after it the grid behaves
   uniformly again.
3. Relative tracking (pedal deltas scale the stored gain). Reproducible AND
   fadeable, but if the pedal was low at recall, pushing to full toe
   multiplies the chord well past its saved loudness, and a recall at pedal
   = 0 has no defined ratio. I'd avoid it.

Which do you want? (If 2, note one consequence: recalling with the pedal at
heel and then twitching it will duck the chord toward silence -- correct
under the rule, but worth knowing.)

* ONGOING recall: does re-pressing a sounding slot stack, restart, or stop it -- and how does ONE chord stop?
Unspecified, and it decides how the instrument feels:

- My recommendation: a slot press *restarts* its own chord -- if voices from
  this slot's previous recall are still ringing, kill them and spawn fresh.
  No unbounded stacking from repeated presses, and re-striking a chord is a
  musical gesture. Different slots layer freely (the save rule already
  implies chords co-sound).

  doubling (all voices start at phase 0, so two copies are a 2x amplitude

* ONGOING pitch collisions: a chord voice vs a finger at the same pitch
Today, re-fingering a pitch that is sustaining "cuts the old drone and the
new note replaces it; the pitch stays in the set, so releasing the new finger
re-drones it" (readme). The natural extension, which I recommend:

- Fingering a pitch that a chord voice is sounding cuts that chord voice's
  audio; the finger's note takes over (with the *grid's* current timbre and
  pulse, as any fingered note). On release, the chord voice re-drones at its
  own stored parameters -- the chord reason survived the interruption.
- Recalling a chord while one of its pitches is already fingered: the chord
  voice for that pitch spawns silent (swallowed by the finger) and drones
  when the finger lifts.

The alternative -- let both sound -- breaks the one-voice-per-pitch-per-grid
model everywhere (LED reflection, edit handles, the held map) for a case
that mostly produces phase-doubling. Confirm the swallow rule, or say
otherwise.

* ONGOING (probably) editing a chord voice re-homes it: chord reason -> sustained
The vision's edit rules meet the branch-3 rule ("entering edit mode adds the
voice to the sustained set; exiting sustain ends the voice") in a corner
worth deciding deliberately: if a chord voice enters edit mode, it gains a
Sustain reason -- and then what kills it, and does the chord reason shield it

Cleanest answer, which I intend: *any gesture that gives a chord voice a
sustain or edit reason converts it into an ordinary sustained voice* -- the
chord reason is dropped at that moment. Its link to the slot was already
severed (mutations never write back), so nothing is lost; afterwards every
existing rule applies verbatim, with no three-way reason cross-product. The
"recall, mutate, store to a new slot" loop works exactly as you wrote:
recall, edit (the voices are now sustained), save -- the save captures

sustain *off* then ends it (per branch-3's rule) instead of leaving a

* DONE recalled voices arrive in NO edit mode, and re-strike their envelope
Two "what not to store" items important enough to pull out:

- Edit/sustain membership is not stored. If a voice was in edit mode when
  saved, recalling the chord must NOT re-enter edit mode -- otherwise a
  recall would flip the grid into a pitch-picker as a side effect of playing
  a chord. Recalled voices carry the chord reason only.
- Envelope position is not stored. A recall is a strike: attack + pluck
  decay run from the top, like fingering the chord. (The stored amplitude is
  the voice's *gain*, which the envelope then shapes.) A saved voice deep in
  its pluck decay therefore comes back brighter than it sounded at save
  time -- that's what "playing a chord" means, and storing envelope state
  would make recalls weaker every generation.

* DONE timbre switching in edit mode: what does the strip's radio do?
The parenthetical ("Switching timbre should apply ... to any note in edit
mode") has a precedent: the factored-pulse multipliers, which in edit mode
retune the edited notes INSTEAD of moving the grid's tempo factor. I
recommend the same shape: while any note on a grid is in edit mode, a
waveform-strip press retimbres the edited notes (full timbre slot: waveform
+ AM/FM params + gain, crossfaded over a few tens of ms to avoid the
discontinuity click) and leaves the grid's future-note timbre alone.

The wrinkle is display: the strip is a radio showing the grid's timbre. If
an edit-mode press doesn't move the grid timbre, the radio doesn't move
either -- you get feedback in the sound but not the LEDs. Alternatives (show
the edited notes' timbre while edit mode is active -- ill-defined when edited
notes have different timbres; or let the press move both the notes and the
grid radio -- simple, visible, but changes future notes as a side effect).
Which behavior do you want? My lean: press acts on edited notes only, radio
stays put, accept the LED silence.

(The smoothing itself I'm confident about: an equal-power crossfade on the
one voice, phase carried over where the waveforms share the accumulator. It
will be the plan's business, not this doc's.)
