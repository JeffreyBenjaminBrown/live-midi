*** Claude to Jeff : yes, TOML nests; here's the proposed org syntax
Full design + migration plan: [[file:TODO/toml-to-org-rig-format.org]]. Short version:

TOML has three shapes we must mirror: scalars (=k = v=), *tables* =[a]= (which
DO nest, dotted: =[a.b]=), and *arrays of tables* =[[a]]= (repeatable). So one
=TABLE= keyword isn't quite enough -- we need to distinguish "a table" from "one
element of an array of tables." Proposed keywords (headline title prefixes):

- =PARAM key = value= -- a scalar leaf. The value after =\== is ordinary TOML
  value syntax, so inline arrays/tables just work: =PARAM rect = [0, 0, 15, 15]=,
  =PARAM select.size = [16, 16]= (dotted key), =PARAM waveform = "saw"=.
- =TABLE key= -- a (sub)table; its descendant PARAM/TABLE/ELEM headlines are its
  contents. TABLEs nest (a TABLE inside a TABLE == =[a.b]=).
- =ELEM key= -- ONE element of the array-of-tables =key= (== one =[[key]]=
  block). Repeat sibling =ELEM key= headlines to grow the array, in order.
- A headline with none of those prefixes is pure grouping: *transparent* to the
  data (its PARAM/TABLE/ELEM descendants attach to the nearest enclosing
  TABLE/ELEM), existing only to organize + document -- exactly as you described.
- Bodies are documentation; the parser ignores them (so a body may freely refer
  to an ancestral grouping headline, per your note).

The TOML comments become the headline bodies -- these heavily-commented rigs are
a *better* fit for org than TOML. The "shared library" is one org->=Config=
loader (org tree -> =toml::Value= -> existing serde derives), so every current
consumer keeps using the same typed structs and validation; only the front-end
(=load_config_file=) changes from =toml::from_str= to the org loader. I'll queue
implementation after the rename lands. Keyword names (=ELEM= etc.) are easy to
change -- say the word.
