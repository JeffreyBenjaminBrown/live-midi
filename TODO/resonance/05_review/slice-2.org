* Deviations from the plan's "how"
** Where the shared resolution lives, and its shape
'strings/pedal_targets.rs' gains 'resolve_strings_pedals(&Rig,
&StringsParams) -> Result<ResolvedStringsPedals, String>', the
plan's suggestion. 'ResolvedStringsPedals' is a small 'Copy'
struct ('pedal_targets', 'string_energy_pedal'; 'Default' is no
targets and no energy pedal) so the harness gets both values
from one call. 'Settings' and 'LiveParams' still hold the two
as separate fields, as the plan says. The function checks the
channel range and the 16-target cap itself rather than trusting
validation, so an unvalidated 'Rig' errors instead of panicking.
'resolve_settings' calls it only when the play sink has strings
parameters; a sawwave rig gets the default.
** The function the callback calls
'effective_params_and_energy_position(&StringsParams,
&PedalTargetsPerChannel, Option<usize>, &[f32; NUM_PEDALS]) ->
(StringsParams, f32)', pub in 'strings/pedal_targets.rs' rather
than in 'audio.rs', so the harness (slice 5) can call the same
one. It is 'apply_pedal_targets' plus the energy slot (NaN when
'None'). 'audio.rs' keeps a private 'read_pedal_positions' that
loads the atomics.
** The callback copies 'LiveParams' whole
It used to copy two fields out under the lock; it now copies
the struct (about 2 KB with the targets) and releases the lock
at once. Simpler than a four-field tuple, and cheap.
** Publishing is its own function
'pedal_volume::publish_pedal_positions', called once per poll
right after 'reader.pedals()', so a unit test can check it
without a MIDI port.
