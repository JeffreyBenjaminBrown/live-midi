This responds to =1_vision.org=.  I read =ORIENTATION.org=, =rigs/README.org=,
the current two-edogrid rig and its reference, the chord-storage-v2 discussion
and plan, and the live surfaces runtime (especially =keys.rs=, =grid.rs=,
=settings.rs=, =synth.rs=, =chords.rs=, and =chords_persist.rs=).

Verdict up front: nearly all of the machinery exists, but this is not just a
one-monome rearrangement of the current rig.  The vision changes the chord
model in musically important ways: chord voices stop retaining their captured
timbre and loudness, the chord controls apparently shrink from nine slots to
eight, and octave shift becomes a temporary per-slot chord transformation.
Those choices are coherent, but a plan would have to guess at the layout and
at several interaction rules.  The TODO headings below are the decisions I
still need from Jeff before writing that plan.

* What already exists and can be reused

- A whole-monome EDO play surface, a four-cell timbre selector, the shift pad,
  momentary accretion, sustain clear, and chord storage are all live rig window
  kinds.  This work should compose those pieces rather than revive the older
  =sawwave/state.rs= chord implementation.
- The selector already has the useful split behavior that changing timbre
  applies live to an edit selection when there is one, with a short crossfade;
  otherwise it changes future notes.  The new two-target switch is a different
  split (piano layer versus chord layer), but the live retimbre path exists.
- The synth already separates a timbre slot's =gain=, a per-grid volume-fader
  gain, and an expression-pedal gain.  It can therefore change this new control
  without baking the EX-P or master gain into it.
- A horizontal =volume_fader= window exists, but it maps absolute positions
  over a fixed 30 dB range.  The proposed four buttons are relative dB steps,
  so they need a small new window/control kind rather than a differently sized
  existing fader.
- Chord slots already persist atomically under =state/chord-slots/=.  Today a
  stored voice snapshot includes pitch, timbre, loudness, pulse, and phase, and
  different slots can sound at once.  The new shared chord timbre/volume rule
  deliberately supersedes part of that format/recall behavior.
- Current shift-pad octave corners retune the entire edit selection whenever
  one exists; otherwise they scroll the visible register.  Routing them to a
  chosen chord slot is new, but the in-place octave glide exists.
- Square and diamond dances are optional presentation behavior, not required
  for voices to sound or be edited; omitting them is straightforward.

** ONGOING 8. Initial volumes and bounds

The “two and a half dimensions” answer resolves the state model cleanly: each
of the four timbres has a piano-layer base volume, and each timbre also has a
chord-only delta.  Changing a piano base changes both layers for that timbre;
changing a chord delta changes only the chord layer.  The chord delta starts at
0 dB.  What should each piano base start at, and how far may repeated button
presses move either value?  We need finite bounds both to make the control
musically predictable and to prevent an accidental run of =+12 dB= presses
from creating enormous gains.

** Phase clarification; no question unless you want to preserve it

“Phase” here meant the point within each oscillator's repeating waveform cycle.
The current chord-storage-v2 code records those points relative to the lowest
voice, so recall can recreate the chord's instantaneous wave alignment.  That
matters for deliberately replaying a captured beating/waveform relationship,
but it is extra state and ceremony for this simpler pitch-set chord model.
Given your “I think phase can be dropped,” the plan will drop oscillator phase:
each momentary recall starts fresh through the normal short attack, which avoids
a click.  Pulse phase disappears too because this rig has no factored pulse.
