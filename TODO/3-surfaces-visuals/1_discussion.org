** Why one grid dims and the other doesn't

- Monome LEDs have two command families: *binary* on/off and *varibright* (a
  per-LED level 0--15). Our code already sends the varibright form
  (=/grid/led/level/set=) with three levels: 0 (off), *4 (dim)*, 15 (bright).
- A *non-varibright* grid can't do per-LED brightness. When it receives a level it
  thresholds it: *level > 7 -> ON, level <= 7 -> OFF*. This is confirmed in
  monome's own code (=libmonome= =reduce_level_to_bit(level) = (level > 7)= and the
  grid firmware's =rx[3] > 7=).
- So our =DIM = 4= becomes *OFF* on that grid, while =BRIGHT = 15= (> 7) stays *ON*
  on both. That is exactly your report: "active solid on both; the others dim on
  one, off on the other."
- Your two 16x16 grids are a "256" size. The original monome *Series 256* (2007--2010)
  is *monobright* (no per-LED dimming); a modern 16x16 (e.g. monome's 2023 "grid
  zero") *is* varibright. So one of your two is almost certainly a monobright 256 --
  that's the one showing "off" instead of "dim".

** The duty cycle & frequency to fake dimness (your explicit question)

Dimness on a capable grid really is PWM (rapid on/off) inside the LED driver; we can
fake it in software by flashing an on/off LED fast enough to fuse.

- *Frequency:* fuse above the flicker threshold. Cones fuse ~48--60 Hz; peripheral
  vision can still catch flicker up to ~80 Hz. Safe engineering target: *60--120 Hz*
  (period 8--16 ms). Our codebase already flashes "dim" at *66.7 Hz* (15 ms period)
  in =edo12n_piano_monome_runtime= -- I'll reuse that.
- *Duty cycle:* above fusion, perceived *luminance* = duty cycle x full brightness
  (Talbot-Plateau). But perceived *brightness* is compressive (~luminance^0.33..0.43),
  so a "quarter-bright" look needs far less than 25% duty. A *1/32 duty (~3%)* reads
  as a convincing dim -- and, usefully, ~1/32--1/25 duty is about what a varibright
  grid's *native level 4* looks like (its gamma curve maps level 4 to ~4% drive). So
  a 1/32-duty flash on the monobright grid will roughly *match* the varibright grid's
  level-4 dim. That's the number: *~1/32 duty at ~67 Hz.* (Our existing =PulseBrightness=
  helper already expresses exactly this.)

** Is flashing a performance bottleneck? (your explicit question)

Short answer: *the naive way, yes; batched, no -- with one caveat and one required
system tweak.*

- The link is an FTDI serial port at *115200 baud ~= 11.5 kB/s* (~87 us/byte).
- *Naive (one message per dim cell):* trails + dim arrows can be ~30+ cells. Flashing
  30 cells on+off at 67 Hz ~= *4000 messages/s* ~= ~12 kB/s -- that *saturates* the
  link (and worse, see the FTDI note below). So per-cell flashing *is* a bottleneck.
- *Batched (whole-row/quad writes):* a monome "quad" is an 8x8 block; a 16x16 grid is
  4 quads. Repainting the changed quads twice per flash is *4 x 2 x 67 ~= 540 msgs/s*
  ~= ~6 kB/s ~= ~half the link. Fine. So the fix is to *paint the flash as quad/row
  writes, not per cell.* (We currently send per-cell diffs; I'd add a batched path.)
- *Required system tweak:* the FTDI *latency timer* defaults to *16 ms*, which alone
  caps clean updates near ~62 Hz and adds jitter. It must be lowered (to ~1 ms) for a
  smooth 67 Hz flash. This is a known monome/serialosc setting, set on the host.
- *The one honest caveat:* sending a 4-quad frame takes ~3.8 ms, which is *longer than
  a crisp 0.5 ms dim pulse*. So if dim cells are scattered across all four quads, we
  can't actually deliver a true 1/32 duty -- the pulse gets transmit-bound and the dim
  reads *brighter* (toward half-bright) unless we keep the dim set small or lengthen
  the period. This only bites the *monobright* grid, and only when many dim cells are
  lit at once (lots of trails). Mitigations in the plan below.

* Plan

Common groundwork (touches most features): today each grid thread keeps its own
=held= set and its own scroll =register= privately, and =levels_for_grid= paints by a
*register-independent* pitch-class map. I'll (a) make each grid publish its currently-
sounding pitch-classes to a small shared structure, (b) add a shared 7-entry trail,
and (c) switch the LED math to the looper's *register-aware* painter so lit cells move
with the shift. Then each of the six features is a small addition on top.

** 1. Identical waveform strips on both grids

The strip logic is already identical; only the *rendering* of =DIM= differs because
one grid is monobright. Fix = make =DIM= look the same on both by faking it with a
flash on the monobright grid (see research above). Concretely: keep native level 4 on
the varibright grid; on the monobright grid, render dim cells by pulsing them on at
~1/32 duty, ~67 Hz, using batched (row/quad) writes. Selected waveform = solid on both
(15 > 7, already fine).

** 2. Volume control (top row, 12 buttons)

- Window: a new =volume_strip= (or similar) covering the top row right of the wave
  strip: =rect = [4, 0, 15, 0]= (12 cells). One cell lit = current level, rest off.
- Mapping: 12 discrete positions, *logarithmic* = equal dB per step. Spread ~30 dB
  across the 12 -> ~2.7 dB/step. Startup at *column 10* (the 7th of the 12), leaving
  columns 11--15 (5 steps) of headroom to the right.
- Effect: scales the synth's output gain. The synth's =amplitude= is currently baked
  in at stream-build; I'll make it a live value the audio callback reads, and the
  strip writes it. (No flashing needed -- the strip is lit/off, not dim.)
- Default level = the rig's current amplitude (0.15) at column 10; steps left get
  quieter, steps right louder, 30 dB total end-to-end.
- (Per-grid vs global, and cross-control -- see Problems.)

** 3. Cross-grid note reflection

Each grid publishes the pitch-classes it is currently sounding into shared state. When
a grid paints, it lights every cell whose *current-register* class is in the *union* of
both grids' sounding classes. Because each grid uses its *own* register, the same note
lights on each grid wherever that grid currently places it -- octave-equivalents and
all. (This subsumes the existing single-grid reflection.)

** 4. Trails (last 7 notes, dim)

- Add a shared ring buffer of the last 7 pressed notes (as pitch-classes). On each
  note-on (either grid) push its class.
- Paint: a cell whose current-register class is in the trail -> *dim*; if that class
  is *currently held* on either grid -> *bright* (bright clobbers dim). Everything
  else off.
- Dim here is the same faked-dim flash as feature 1 on the monobright grid.

** 5. Lit keys move with the window shift

Adopt the looper's painter (=looper_runtime/state.rs::paint_classes=): compute each
cell's class as =step_for_cell(x_step, y_step, register, x, y) mod edo= using the
*live* register, instead of the current fixed, register-independent map. Then a shift
changes every cell's class, so the lit octave-equivalents of a held pitch move under
the new window -- exactly the looper-timbre behaviour you remembered. (Held *voices*
keep the pitch they were struck at; only the LEDs move.)

** 6. Shift arrows dim, octave corners dark

Falls out of feature 5 for free: the looper painter already lights the four arrows
(=Up/Down/Left/Right=) at =LEVEL_DIM= and leaves the two octave corners dark. Porting
that logic gives you this directly. (The arrows are "dim", so on the monobright grid
they use the same faked-dim flash.)
