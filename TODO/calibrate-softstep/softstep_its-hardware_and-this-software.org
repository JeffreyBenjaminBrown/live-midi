* how both work
The SoftStep is put in *tether mode*, where it streams each pad's *4 pressure
sensors* as Control Change messages, refreshed only *~every 10 ms*. The runtime
*sums a pad's 4 sensors* (0..508) and runs a tiny per-pad state machine:

1. *Onset* -- the sum rising above =ON_SUM= (20) starts a hit (=Idle -> Rising=).
2. *Attack window* -- for =ATTACK= (14 ms) it keeps the *peak* sum seen.
3. *Fire* -- 14 ms after onset it emits one hit whose *velocity* is that peak
   scaled to 1..127, *unless* the same pad fired < =debounce_ms= (50 ms) ago.
4. *Re-arm* -- the pad won't fire again until its sum falls back below =OFF_SUM= (20).

Three independent gates must all pass for a kick to sound: the sum must *exceed
20*, it must *stay above 20 for the full 14 ms* window, and the pad must *not have
fired in the last 50 ms*.

"How hard" = the peak sum over the 14 ms window, mapped to velocity 1..127, then to
a *loudness* spread across a 20 dB range (vel 127 = full, vel 1 = -20 dB).

The two constants most relevant to the symptoms: =ON_SUM= and =OFF_SUM= are *both
20* (there is *no hysteresis gap*), and =debounce_ms= only guards 50 ms. See
[[* Where "no hit" comes from]] and [[* Where "double hit" comes from]].

The old SoftStep device only refreshes its sensors ~every 10 ms
(which rationalizes the 14 ms wait).
The new one (arriving tomorrow) might be faster.

Loudness is ~logarithmic, over a 20 db range.
Velocity is derived entirely from pressure; the KMSS itself has no velocity.

* constants this code uses

| constant              | value  | where                     | role                                                              |
|-----------------------+--------+---------------------------+-------------------------------------------------------------------|
| =ON_SUM=              | 20     | decode.rs:43              | onset: sum must exceed this to *start* a hit                      |
| =OFF_SUM=             | 20     | decode.rs:44              | release: sum must drop below this to *re-arm*                     |
| =ATTACK=              | 14 ms  | decode.rs:45              | how long after onset the peak is captured before firing           |
| =VELOCITY_FULL_SCALE= | 460    | decode.rs:31              | pad sum (0..508) that maps to velocity 127                        |
| =VELOCITY_DB_RANGE=   | 20 dB  | decode.rs:27              | loudness spread from vel 1 to vel 127                             |
| =debounce_ms=         | 50 ms  | config:148 (window field) | min gap between two fires on the *same* pad                       |
| poll interval         | 1 ms   | mod.rs:256                | how often matured hits are checked (device scan ~10 ms dominates) |
| sink =amplitude=      | 1.6    | config:52                 | drum master gain, applied at mix, clamped [-1,1]                  |
| device scan           | ~10 ms | firmware (fixed)          | sensors only refresh ~100 Hz -- the latency/aliasing floor        |

*Note the missing hysteresis gap:* =ON_SUM= and =OFF_SUM= are *both 20*. There is no
dead-band between "start a hit" and "re-arm." (The Python meter uses 40/20 -- see
[[* meter.py disagrees with the runtime]].)
