** What "rng" is
The click sound was *white noise* (random samples) shaped by an
envelope. To generate random samples cheaply on the audio thread, we
use an inline xorshift32 PRNG — its entire state is one u32 named
=rng=. When the click goes away, the rng goes with it.

So: nothing surprising; "rng" was just the noise generator. Confirm.

** Pitch-class index — what it is
This is the data structure I added in commit 2e0ce7c (the lighting
feature). At startup, for each cell on the 16×16 grid, I compute its
=EdoPitch= (the integer =x_step·x + y_step·y= mod =edo=) and store
two maps:

#+begin_src rust
  struct PitchClass {
    key_to_pitch:  HashMap<(i32, i32), EdoPitch>,
    pitch_to_keys: HashMap<EdoPitch, Vec<(i32, i32)>>,
  }
#+end_src

Used by the EDO-grid window: when key (x,y) is pressed, look up its
pitch class, then look up all the other cells that share that pitch
class, and light them all. The "pressed" set tracks who's currently
held so we know when to turn them off. None of this changed in the
accretion work — it'll just be one of several "reasons a cell is lit"
in the new model.

** Reason_Its_On — what it is
The new bookkeeping I'm proposing for the accretion era. Today, a
cell is lit only because some pitch-equivalent key is pressed. Soon
it could be lit because:
  (a) a pitch-equivalent key is pressed,
  (b) its pitch is in the emitting slot,
  (c) it's a control cell for the accretion UI.

We need to know "all the reasons this cell is currently lit," so
that when one reason goes away (a key is released; emit toggles
off; etc.) we can correctly decide whether to send the LED-off
command. Concretely:

#+begin_src rust
  enum LedReason {
    PitchEquivalent { source_xy: (i32, i32) },  // (a)
    InEmittingSlot  { pitch:     EdoPitch },    // (b)
    // (c) is owned by the control window; see "ownership" below.
  }
  // Sparse: only cells with ≥1 reason appear here.
  type LedReasons = HashMap<(i32, i32), HashSet<LedReason>>;
#+end_src

When a reason appears or disappears, we update the relevant cells'
sets. A cell goes lit when its set transitions from empty → ≥1, dark
when it transitions back. Just two LED commands per state change,
not 256.

** Window ownership of cells (the part you asked me to elaborate)

** VoiceState fields — what each one is and why

Replying inline to your TODOs:

  - =freq: f32= — Hz. The audio frequency this voice produces. Per
    sample, =phase += freq / sample_rate=.
  - =phase: f32= — in [0, 1). Position within one cycle of the
    triangle wave. We need this so audio is continuous across
    callback boundaries (otherwise every block would restart the
    wave at zero, which sounds like a click).

    This is "phase" in the audio-engineering sense — yes, the same
    sense you meant when you said "don't coordinate phase." Each
    voice has its own =phase=, evolving independently. We never
    align two voices' phases.
  - =env: f32= — in [0, 1]. The voice's current amplitude scalar.
    Output sample = =triangle(phase) * env * AMPLITUDE=.
  - =target_env: f32= — the value =env= is currently moving toward.
    Yes, also 0 sometimes — for normal release, target_env = 0;
    for the release-into-accretion transform, target_env = 0.5; for
    attack, target_env = 1.0.
  - =ramp_per_sample: f32= — Δenv per audio sample, set when a new
    ramp starts. Computed so the ramp finishes in the chosen time
    (3 ms attack ⇒ ramp = (target - env) / (0.003 * sample_rate)).
    Each sample: =env += sign(target_env - env) * ramp_per_sample=,
    clamped at target.
  - =releasing: bool= — you're right, this is redundant once we have
    target_env. "Releasing" just means =target_env < env=. Drop the
    field; check the relation when we need to.

So the final shape:

#+begin_src rust
  struct VoiceState {
    freq: f32,
    phase: f32,
    env: f32,
    target_env: f32,
    ramp_per_sample: f32,
  }
#+end_src

A voice is removed when =env = 0= AND =target_env = 0=.

Sound right?

** Retrigger: (a) vs (b), shapes side by side

You asked which is actually simpler. Here are the press-handler
bodies for the same scenario (key (x,y), pitch P) under each rule:

*** (a) Retrigger keeps the same UUID
#+begin_src rust
  let entry = finger_voices.entry((x, y));
  match entry {
    Entry::Occupied(mut e) => {
      // Voice exists (mid-release or sustained). Just re-aim its
      // envelope back at full. UUID and phase carry forward.
      let v = e.get_mut();
      v.target_env = 1.0;
      v.ramp_per_sample = (1.0 - v.env) / (ATTACK_SECS * sample_rate);
    }
    Entry::Vacant(e) => {
      let id = next_uuid();
      e.insert(VoiceState { freq, phase: 0.0, env: 0.0,
                            target_env: 1.0,
                            ramp_per_sample: 1.0 / (ATTACK_SECS * sample_rate),
                            id });
    }
  }
#+end_src

This is what the existing code does today (minus the UUID); the
voice carries forward across retriggers.

*** (b) Retrigger issues a new UUID
#+begin_src rust
  let id = next_uuid();
  finger_voices.insert((x, y), VoiceState {
    freq, phase: 0.0, env: 0.0,
    target_env: 1.0,
    ramp_per_sample: 1.0 / (ATTACK_SECS * sample_rate),
    id,
  });
  // Note: this drops any existing voice at (x,y) mid-release.
  // The slot may still hold the dropped voice's UUID, which is
  // now dead. Liveness is checked via "does any voice in
  // finger_voices currently bear this UUID?"
