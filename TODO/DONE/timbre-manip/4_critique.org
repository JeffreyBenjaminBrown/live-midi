***** context (claude): what this TODO is about, term by term
You asked me to define every term before using it, so this builds from scratch.

- *Loop*: a short musical phrase that is recorded and then repeats. The companion
  "looper" feature (=TODO/monome-looper/=) records and plays loops.
- *Loop note*: one note inside a loop, stored as pitch + timing. This feature adds
  one field to each loop note: its timbre (next).
- *Timbre*: the tone-colour of a note -- its waveform, volume, tremolo (= AM,
  amplitude modulation), vibrato (= FM, frequency modulation), and wave shape.
  Everything about how a note sounds *except* its pitch and timing.
- *Per-note timbre*: each loop note carries its own timbre, captured at the moment
  it was recorded ("record-time capture"). So one loop can hold a saw note, then a
  sine note, etc.
- *Loop slot*: a numbered storage location holding one whole loop. The looper has a
  grid of these; pressing a slot recalls/plays the loop in it. The looper also has
  a *copy gesture* that copies one slot's contents into another.
- *Trigger (a loop)*: press its slot to start it playing.
- *Loop-timbre editor*: the on-grid window where you change a playing or selected
  loop's timbre (defined at 3a/5b).
- *Destructive editing*: the headline of this feature. Editing a loop's timbre via
  the loop-timbre editor *permanently rewrites* the stored per-note timbre of the
  affected notes -- it is not a temporary overlay you can drop. (Your explicit
  choice at 2_discussion 1c, "both should be destructive.")

Because editing is destructive, there is no natural undo -- the old timbre values
are simply overwritten and gone. So you proposed a cheap one:

- *Failsafe duplicate slot*: one loop slot reserved as an automatic backup that
  always holds a copy of a loop *as it was before your edits*. To undo, you use the
  copy gesture to copy that backup back over the slot you edited. It is coarse: it
  restores the *whole* loop at once, not individual edits -- hence "massive undo"
  (all-or-nothing, per slot).
- *Snapshot*: the act of copying a loop's current contents into the failsafe slot.

The TODO is *when the snapshot is taken*, because that decides whether the backup
actually holds a pre-edit copy when you reach for it. Two options:

- *Trigger-time snapshot* (what you originally specified): the failsafe copies a
  loop at the moment you *trigger it to play*, and is overwritten the next time any
  loop is triggered.
- *Copy-on-first-edit* (a.k.a. *copy-on-write*): the failsafe copies a loop the
  *first time you edit it* since it was last triggered -- i.e. the instant before
  the first change.

Why I flagged trigger-time as leaky:
1. If you *re-trigger* the loop you are editing (say, to hear it from the top), the
   trigger-time rule snapshots it *again*, now capturing the already-edited state.
   Your pristine backup is gone and undo no longer works.
2. *Selection edits* (1a: editing a chosen set of loop notes) apply *immediately*
   and don't need the loop to be playing -- so you can edit a loop you never
   triggered this session, which trigger-time never backed up. Unprotected.

Copy-on-first-edit closes both: the backup is taken right before the first edit,
whatever triggered it, so it is always the true pre-edit state -- at the same cost
of one slot. That's why I recommend it; but it changes the rule you wrote, so the
call is yours.
