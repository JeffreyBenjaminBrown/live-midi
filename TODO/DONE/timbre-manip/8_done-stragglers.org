** 1. Make =save_undo_double_ms= config-driven  [DONE]
DONE: =save_undo_double_ms= is now a per-editor config field (default 200; read off the
loop editor in =resolve_settings=, threaded to the runtime). The hardcoded literal in
=run()= is gone. Tests: a config parse test (default + explicit) + the resolve test
asserts the window. 208 bin + 40 lib green. The notes below are the original write-up.
*** What it is
The save-undo button distinguishes a single tap (set a checkpoint) from a double tap
(revert) by a time window (6_plan 2.8). 6_plan 5 sketches that window as a per-editor
config field =save_undo_double_ms = 200=. Today the *value flows through the runtime*
correctly, but its *source* is a literal, not the config.

*** Why it's imperfect
- =looper_runtime/mod.rs:359= -- =run()= sets =save_undo_window: Duration::from_millis(200)=
  with a comment "until that field is threaded through config (a trivial follow-up)".
- So a user can't change the double-tap window without editing Rust.

*** The fix (small; ~15 min, low risk)
The plumbing already exists end to end -- only the config *source* is missing:
- =config.rs:480= =TimbreEditor { .. }= variant: add
  =#[serde(default = "default_save_undo_ms")] save_undo_double_ms: u64= (default 200),
  and a =fn default_save_undo_ms() -> u64 { 200 }=. Optionally expose it via a small
  accessor like the existing =timbre_editor_rows()=.
- =mod.rs= =resolve_settings=: read it off whichever timbre_editor window has it (the
  loop editor is the one with save-undo), put it on =Settings=.
- =mod.rs:359= =run()=: replace the literal with =Duration::from_millis(s.save_undo_ms)=.
- =state.rs= already carries it: =LooperParams.save_undo_window= (=state.rs:135=) ->
  =LooperState.save_undo_window= (=state.rs:59,252=) -> used in =save_undo_press=
  (=state.rs:434,438=). No state changes needed.
- Test: a config-parse test asserting the field reads back; the existing
  =save_undo_*= state tests already cover the behaviour (they pass =ms(200)= directly).

*** Risk / caveat
Essentially none. It's additive config with a default, so every existing config is
unchanged. The only "decision": which window owns the field if both editors are
present -- the *loop* editor (save-undo is loop-only; inert in the live editor).

** 2. Exact "hold last on rests" in the loop-editor display  [DONE]
DONE: =LooperState.loop_display_held= now remembers the lowest sounding loop timbre
(updated each =playback_tick=, held across rests AND loop wraps), and =displayed_timbre=
returns it on a rest before falling back to the live timbre. Cleared in
=reconcile_playback= when playback stops or the sounding slot changes. Taste calls
taken: hold across wraps; clear on stop / active-slot change. Test: play a 1-note loop,
tick past the note-off into a rest -> the editor still lights the held note; stopping
falls back to the live timbre. 209 bin + 40 lib green. The notes below are the original
write-up.
*** What it is
The loop-timbre editor's rows show the timbre of the note under the playhead. 6_plan
2.4 says: "on a rest it holds the last value" -- i.e. between notes, the display should
keep showing the *most recent* note's timbre, not jump to something else.

*** Why it's imperfect
- =state.rs:541= =displayed_timbre()=: under a selection it shows the lowest selected
  note; while a note sounds it shows the lowest still-sounding note (=state.rs:565=
  =lowest_sounding_loop_timbre=); but on a *rest* (nothing selected, nothing sounding)
  it falls back to the *live timbre*, not the last note's timbre. See the doc-comment
  at =state.rs:539-540=.
- Practically: as a loop plays, between notes the editor rows momentarily reflect the
  live timbre instead of holding the last note you heard. Cosmetic, but not spec.

*** The fix (small-medium; the subtlety is WHERE to remember)
=displayed_timbre()= is =&self= (it's called from =edo_levels=, a read-only paint). To
"hold last" you must *remember* the last non-rest timbre, which needs a write. The
natural write point is the playback tick:
- Add =loop_display_held: Option<Timbre>= to =LooperState=.
- In =playback_tick= (where you already know the sounding notes), when something is
  sounding, set =loop_display_held = Some(lowest_sounding_timbre)=. Leave it untouched
  on a rest (that's the "hold").
- In =displayed_timbre()=, the rest branch returns =loop_display_held= (if any) instead
  of =live_timbre=. Selection + sounding branches are unchanged and take priority.
- Decide a reset rule: clear =loop_display_held= when playback stops or the active loop
  changes (otherwise it holds a stale colour from a different loop). Probably clear it
  in =reconcile_playback= when =sounding= goes to =None= or the slot changes.
- Test: record a 1-note loop, play, tick PAST the note's note-off into a rest, and
  assert the editor still lights the held note's waveform cell (today it would show the
  live timbre). Mirror =loop_editor_display_tracks_the_lowest_sounding_note= (=state.rs=
  test) but step the playhead into the gap.

*** Risk / caveat
Low, but two judgement calls are yours:
- *Reset semantics*: hold across the loop's wrap? I'd clear on stop and on active-slot
  change, but hold across wraps (so a rest at the loop seam still shows the last note).
- *Does it matter to you?* It's a momentary flicker between notes. If you don't find it
  bothersome in practice, skipping this is completely fine -- the current behaviour is a
  reasonable approximation, just not the letter of 6_plan 2.4.
