** Free functions vs =impl= blocks

Direct answer to your aside: in Rust there are basically three
reasons to write =impl Type { ... }= rather than free functions
that take =&Type= or =&mut Type=:

  1. *Trait impls* (=impl Clone for Foo=, =impl Debug for Foo=,
     etc.). These have to be impl blocks; the language requires
     it. We use them all the time via =#[derive(Clone, Debug,
     PartialEq, Eq, Hash)]= on struct/enum definitions. Those
     stay on the type declaration itself in =types.rs= — they're
     declarations *about* the data shape, not behaviour we wrote.
  2. *Method-call syntax* (=foo.bar()= vs =bar(&foo)=). Pure
     ergonomics, no semantic difference. Affects discoverability
     in IDEs (=foo.= autocompletes to all methods) but not
     behaviour.
  3. *Associated functions* (=Foo::new(...)= as a constructor) —
     these are conventionally =impl=, but a free function
     =new_foo(...)= is identical.

There's no semantic capability you lose by using free functions
for our own behaviour. Generic constraints (=where T: Trait=) and
trait-bound dispatch work identically.

So my proposal for the refactor:
  - =#[derive(...)]= attributes stay on type declarations in
    =types.rs= (they're metadata, not behaviour).
  - All hand-written =impl Type { fn ... }= methods become free
    functions: =fn edo_press(state: &mut AppState, cell: Cell) ->
    Vec<LedCmd>= instead of =impl AppState { fn edo_press(&mut
    self, cell: Cell) -> ... }=.
  - Trait impls we have to write by hand (none today, but if any
    show up: =impl Display for ...= say) live in the domain
    module, not =types.rs=.

OK?
