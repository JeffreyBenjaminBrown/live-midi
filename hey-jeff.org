This file holds the open questions from the debounce work in =queue.org=. I
finished the parts I was sure of, and I described those finished parts in
=queue.org=. This file holds only the decisions that I could not make on my own.
I wrote every question in complete sentences, and I defined the technical terms
in the glossary at the bottom.

* Question 1: should the =1 pedal also get the Settle debounce?
I left the =1 pedals unchanged, so they still use the Standard debounce and not
the new Settle debounce. I made this choice for a specific reason. The double-tap
dance needs two quick presses in a row, and the Settle window would swallow the
second press before it could register. The =1 pedals still have the ordinary
min-gap guard that every pad shares.

I need you to tell me whether the =1 pedals bounce when you press them. If they
do bounce, then I will design a gentler guard for them. That gentler guard would
still let the double-tap dance work.

* Question 2: should a drum pad keep watching after you lift your foot early?
You told me that a drum pad should keep watching until its amplitude window has
passed, even when you lift your foot before that window closes. Today a drum pad
does the opposite, because it stops the moment you lift, even when its amplitude
window is still open. I did not change this behavior yet. I held off for two
reasons. No rig uses drum pads at the moment, and this change would alter how
every drum pad behaves.

I need you to tell me whether I should make this change. If you say yes, then I
will make a drum pad ignore an early lift until its amplitude window closes.

* Question 3: where should the debounce settings live?
You asked me to make the debounce setting a per-rig parameter, and you asked me
to move the meter's configuration into the meter's own folder. I have not done
either of these things yet, and I kept the single shared file instead. I want to
explain my hesitation before you decide.

The runtime and the meter both read one shared file today, and that file is
=rigs/softstep.toml=. This one shared file guarantees that the meter shows
exactly the numbers that the runtime will act on. If I split the settings so that
each rig carries its own copy, and if I also give the meter its own copy in its
folder, then those copies can drift apart without any warning. You have asked me
before to hunt down bugs of exactly this shape, where one fact lives in two
places and only one copy gets updated.

I need you to choose one of two paths. The first path keeps the single shared
file, and that is what I did. The second path splits the settings so that each
rig carries its own, and it gives the meter its own configuration in its own
folder. The second path accepts that the two configurations can drift apart.

* Question 4: is a per-kind rule enough, or do you want a per-pad override?
You said that whether a pad debounces should be a property of the pad. I built
this as a per-kind rule. A factor pedal uses the Settle debounce, and every other
kind of pad uses the Standard debounce. I did not add a way to override a single
named pad in the rig file.

I need you to tell me whether the per-kind rule is enough. If you want to force
one specific pad to settle, or if you want to force one specific pad not to
settle, then I will add a per-pad setting to the rig file.

* Question 5: which pads did you mean by "the sustain and edit pads on the other monome"?
One sentence in your note confused me, and it was the sentence about "the sustain
and edit pads on the other monome." In the current rig, a musician sustains and
edits notes by pressing monomekeys. A monomekey sends a clean press that carries
no pressure and cannot stick. A stuck sensor is a softstep problem, and it is not
a monome problem. I therefore guessed that you meant the softstep accrete pedals.
Those accrete pedals stay on the Standard debounce, and they already read zero
after 25 milliseconds of silence.

I need you to confirm that guess, or I need you to point me at the pads you
actually meant.

* Glossary
- Standard :: Standard is the debounce mode that every pad used before this work,
  and it is the mode that most pads still use. A pad in Standard mode fires the
  moment its pad sum crosses the on-threshold. It then watches for a louder peak
  through its amplitude window. It re-arms once its pad sum falls below the
  off-threshold. It also refuses to re-fire within a short fixed min-gap after its
  last fire. This mode suits a drum pad, because a fast double-tap on a drum is
  two real hits. It also suits a held pedal such as an accrete pedal, because
  every genuine press counts and a lift must register at once.
- Settle :: Settle is the aggressive debounce mode that I added for the timing
  pedals. A pad in Settle mode fires once, and it then emits no louder-peak
  updates. It refuses to fire again until its pad sum has held perfectly steady
  for a set time and has also fallen back below the off-threshold. The set time is
  150 milliseconds by default. A single stomp makes the pad sum jitter as the foot
  rocks, and that jitter keeps resetting the steadiness clock, so one stomp
  produces exactly one event.
- timing pedal :: A timing pedal is one of the four tempo-factor pedals, which are
  the =x2=, =x3=, =/2=, and =/3= pedals. Each one multiplies a grid's tempo
  factor. I gave these pedals the Settle debounce. Some people also call these the
  factor pedals.
- =1 pedal :: The =1 pedal is the pedal that switches a grid's factored pulse on
  and off. The word Unity also names this pedal in the code. This pedal is not a
  timing pedal, and it runs its own double-tap dance.
- double-tap dance :: The double-tap dance is the sequence of =1 presses that
  turns a grid's factored pulse off. A first press snaps the tempo factor to
  unity, and a second press within 400 milliseconds turns the factored pulse off.
- accrete pedal :: An accrete pedal is a softstep pedal that sustains notes. A
  musician holds it to add notes to a grid's sustained set, and the musician
  releases it to stop adding notes.
- drum pad :: A drum pad is a softstep pad that plays a drum sample when a foot
  strikes it. No rig uses drum pads at the moment, though the code still supports
  them.
- pad sum :: A pad sum is the sum of a pad's four pressure sensors. The decoder
  compares this pad sum against the on-threshold and the off-threshold.
- amplitude window :: The amplitude window is the short span after a pad fires,
  during which a louder peak can raise the note's volume. This window lasts about
  14 milliseconds by default.
- de-stick :: De-stick is the rule that a sensor which has sent no reading for a
  set time reads as zero. This rule frees a pad whose sensor has physically stuck.
  The set time is 25 milliseconds today.
- the meter :: The meter is the =softstep_meter= program. It shows every pad's raw
  pressure so that you can see what the hardware is sending. It reads the same
  =rigs/softstep.toml= file that the runtime reads.
- monomekey :: A monomekey is one button on a monome grid. A monomekey sends a
  clean press and a clean release, and it carries no pressure reading.
