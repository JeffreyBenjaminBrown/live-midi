#+title: Synth (Rust drumkit) vs. meter -- how their hit detection & pressure differ
#+date: 2026-07-05

* Overview | purpose
Two programs decode the SoftStep's tether stream into hits with a strike pressure:

- *the kit* -- =edo_surface/src/drumkit_runtime/= (=decode.rs= is the state machine,
  =audio.rs= plays the samples). This is the instrument that actually makes drum sound.
- *the meter* -- =tools/softstep/meter/main.py=. A diagnostic tool: live pressure
  bars, a pressure-scaled audition, and per-pad =.org= logs. It is *meant* to mirror the kit so
  what you calibrate here matches what you'll hear there.

They share the same *shape* of algorithm (fire on onset, watch for a higher peak over an
attack window, re-arm on release, de-stick a silent sensor), and -- since the
=softstep.toml= change -- most of the same *knobs*: the kit reads them from the shared
=rigs/softstep.toml=, the meter from its own =config.toml=, with matching defaults for
onset, release, attack, pressure and de-stick. *Debounce is the one exception, and it has
since gone the other way -- from matching to diverged* (see [[* 1. Debounce -- diverged, not shared]] below): the kit reworked its re-fire guard into something the meter's
=config.toml= has no equivalent knob for at all. What still differs is below.

* The parameters, side by side

Both sides are config now, and most defaults still match -- debounce is the exception,
flagged in its own row:

| knob                     | kit (rigs/softstep.toml)  | meter (meter/config.toml) |
|--------------------------+------------------------------+---------------------------|
| onset threshold          | =on_sum= 20                  | =on-sum= 20               |
| release threshold        | =off_sum= 20                 | =off-sum= 20              |
| attack watch window      | =attack_ms= 14               | =attack-ms= 14            |
| retrigger guard *(diverged -- see section 1 below)* | =factor_release_ms= 25 (quiet gate) + =factor_settle_ms= 150 (Settle pedals only) | =debounce-ms= 100 (fixed min-gap, unchanged) |
| sum-of-4 -> full pressure 1.0 | =pressure_full_scale= 460    | =pressure-full-scale= 460      |
| pressure loudness spread | =gain_db_range= 20 dB    | =gain-db-range= 20         |
| sensor de-stick          | =silence_to_zero_ms= 25 ms   | =silence-to-zero-ms= 25   |

*The remaining gotcha:* they are still *two files*, not one source. The kit reads
=rigs/softstep.toml=; the meter reads =tools/softstep/meter/config.toml=. Edit one
and not the other and they drift -- so the meter can be tuned lighter than the kit (or vice
versa), and the meter's numbers only predict the kit if you keep the two files in step. The
final unification would be to have the meter read =softstep.toml= directly for the shared
knobs (see [[* If you want them fully unified]]).

* 1. Debounce -- diverged, not shared

This used to be the one gap where the meter lacked what the kit had (a fixed
=debounce_ms= / =debounce-ms= min-gap in both, matching defaults of 100 ms). That gap is
closed now, but the wrong way round: the *kit* has since moved off the fixed min-gap
entirely, while the *meter* still has it. They no longer implement the same mechanism --
=rigs/softstep.toml= does not even have a =debounce_ms= key any more -- so do not read
this section as "both debounce the same way, just check the numbers." They don't.

- *Kit:* a quiet gate, not a min-gap (=DebounceMode::Standard=, in
  =edo_surface/src/drumkit_runtime/decode.rs=). A pad may fire again only once its
  sum-of-4 has gone *quiet (unchanged)* for =factor_release_ms= (default 25 ms, in
  =softstep.toml=) -- *in addition to* the existing requirement that it first release
  below =off_sum=. A contact bounce keeps the sum changing, so it never goes quiet and
  cannot re-fire mid-bounce; a genuine second hit follows a settled release and fires
  normally, however soon after the first it comes. Per-pad, so two feet hit together both
  still fire. This replaced the fixed min-gap because a fixed window both leaked (a slow
  bounce can outlast it and still double-fire) and blocked legitimate fast taps (a real
  hit landing inside the window was swallowed too).
  The tempo-factor pulse pedals (x2, x3, div2, div3 -- but *not* the =1/unity= pedal) get
  a second, stricter mode layered on top, =DebounceMode::Settle=: they fire once on
  onset, emit no =Revise=, and only re-arm once *both* =factor_settle_ms= (150 ms) has
  passed since that fire *and* the pad has been inactive for =factor_release_ms= (25 ms).
  This exists because a rocked or held pulse pedal can re-cross =on_sum= many times per
  stomp -- one stomp reading as =x2^10= instead of a single =x2= -- in a way the quiet
  gate alone did not fully catch.
- *Meter:* unchanged since the debounce it gained earlier -- still the original fixed
  onset-to-onset min-gap, =debounce-ms= (default 100, in =config.toml=), used in both the
  live audition and the =.org= =interpret_hits= re-derivation: after a fire, another
  onset on the *same* pad within 100 ms is *suppressed* outright, still *in addition to*
  a release below =off-sum=. This is exactly the mechanism the kit has since moved away
  from, with the same failure modes the kit's doc comments call out: a slow bounce past
  100 ms still double-fires, and a genuine fast tap inside 100 ms is dropped.
- *Consequence:* =debounce-ms= in the meter's =config.toml= no longer corresponds to
  anything in the kit -- there is no dial in =rigs/softstep.toml= it mirrors. Tuning it
  changes what the meter shows and auditions, but does not predict how the kit handles a
  bounce or a fast roll; for that, read =factor_release_ms= and =factor_settle_ms=
  above instead. The meter's Python (=main.py=, =config.toml=) has not been changed to
  follow the kit's rework -- whether to do that is a separate call, not a doc fix.

* 2. Fire timing and the loudness envelope

Both now *fire on onset* (even a one-sample tap counts) and take the *pressure from the
peak* over the attack window. What differs is what happens between onset and peak:

- *Kit:* fires a voice *immediately* at the onset pressure, then sends =Revise= events as
  a higher peak arrives, *ramping the voice's gain up* to the peak (one-pole de-zipper,
  ~5 ms, in =audio.rs=). The sound *swells* from onset loudness to peak loudness.
- *Meter (live audition):* can't ramp a =pw-play= one-shot, so it fires *once, at window
  close* (on release, or when =attack-ms= elapses), at the *peak* pressure, at a fixed
  volume. You hear the final (peak) loudness, a few ms later than the kit's onset.
- *Meter (=.org= interpretation):* =interpret_hits= reports each hit's time as the *onset*
  and its pressure as the *peak* -- so the *log* matches the kit's fire time and final
  loudness, even though the live audition's timing does not.

* 3. Poll cadence

- *Kit:* a dedicated timer polls the decoder every *1 ms*, so onset-fires and mid-window
  revises are prompt.
- *Meter:* the state machine advances on each incoming CC (the reader) *and* on the
  ~*20 ms* draw tick. So a window-elapsed fire or a de-stick re-arm can lag up to ~20 ms.
  Fine for a meter; the kit is tighter.

* 4. What is actually the same

- *Onset test:* strict =sum > on-sum= (not >=).
- *Pressure:* =pressure = clamp(peak / full_scale, 0, 1)= (kit =pressure_from_peak=,
  meter =_pressure=). Identical formula and, at the shared defaults, the same =full_scale= (460).
- *Loudness curve:* pressure spread over =gain-db-range= dB (pressure 1 -> unity gain, 0 ->
  -range). Identical.
- *De-stick:* per-sensor; a sensor silent longer than =silence-to-zero-ms= reads 0, which
  trips the release path and re-arms the pad. Same mechanism, same default (25 ms).
- *State-machine shape:* idle -> watching (fired) -> held -> idle; re-arm on release.

* 5. Meter-only machinery (the kit has none of this)

- *Event grouping + logging:* =event-group-separation-threshold= / =group-end-hold-ms=
  drive per-pad =logs/pad-<label>/<N>.org= files (raw sum trace + a re-derived
  interpretation). The kit just plays; it never groups or logs.
- *=f= flush* (and flush-on-kill).
- *One reference sample:* the meter auditions a single =audition-sample= (snare) for
  *every* pad -- it's a touch/pressure meter, not the kit. The kit plays each pad's own
  mapped sample (kick, snare, ...), through a 64-voice polyphonic pool with voice stealing;
  the meter spawns an independent =pw-play= per hit.

* 6. Final gain staging (minor)

- *Kit:* voice gain = =pad.gain= (per-pad config) x =gain_from_pressure(pressure)=, summed
  across voices x sink =amplitude=, clamped to [-1, 1].
- *Meter:* =pw-play --volume= = =master-volume= x =gain_from_pressure(pressure)=, clamped to
  [0, 1], one process per hit.

* If you want them fully unified

The onset/release/attack/pressure/de-stick gap is closed: the meter shares those
thresholds' *values* with the kit, and the kit's are no longer hard-coded consts -- they
live in =rigs/softstep.toml=. For those knobs, "calibrate in the meter, then hear it in
the kit" works, as long as you keep the meter's =config.toml= in step with
=softstep.toml=.

Debounce is the exception, and keeping the numbers in step will not fix it: the kit and
the meter no longer implement the same *algorithm* for it (quiet gate + Settle, vs. a
fixed onset-to-onset min-gap), so there is no value you can put in =debounce-ms= that
reproduces the kit's behaviour. Really unifying that seam would mean giving the meter its
own quiet-gate (and, for parity with the tempo-factor pedals, Settle) implementation, not
just a shared number -- a code change, not something this doc can paper over.

The other remaining seam is that the still-matching knobs live in *two files*. The final
step -- if the manual sync of those ever bites -- would be to have the Python meter read
=rigs/softstep.toml= directly for =on_sum=, =off_sum=, =attack_ms=,
=pressure_full_scale=, =gain_db_range= and =silence_to_zero_ms=, keeping its own
=config.toml= only for meter-only settings (grouping, audition, master volume, and its
own =debounce-ms= unless/until the algorithm itself gets unified). Then there is a single
source of truth for everything but debounce.
