* midi_pulse runtime notes

These notes preserve the useful operating details from the old
per-runtime directories that were folded into the config-driven
~midi_pulse~ binary.

Run configs from the repository root:

#+begin_src sh
cargo run --bin midi_pulse -- CONFIG_NAME
#+end_src

For example:

#+begin_src sh
cargo run --bin midi_pulse -- edo12n-piano
cargo run --bin midi_pulse -- edo12n-piano-monome
cargo run --bin midi_pulse -- edo-un12-31-loose
cargo run --bin midi_pulse -- monome-edo-midi
cargo run --bin midi_pulse -- monome-edo-sawwave
#+end_src

* 12n piano

The 12n piano transformer maps MIDI keyboard notes to multi-channel
output for 72-EDO by default.

For piano notes 21-96:

- subtract the lowest A, 21
- divide by 12
- add the quotient to the output channel base
- multiply the remainder by the configured EDO-per-12 value and add
  it to the output note base

The top offset-control range in the default config is notes 97-108.
With ~zero_note = 102~, F#7 means no offset, G7 means +1, F7 means -1,
and so on. Held offset notes change the stored shift for any pitch
class played while they are held.

The optional display config opens an X11/minifb pitch-class grid.
Inside the Docker container, the host must allow X11 access, for
example:

#+begin_src sh
xhost +local:
#+end_src

The container also needs the X11 socket mounted and ~DISPLAY~ set.

* 12n monome offset board

The default ~edo12n-piano-monome~ config uses a 16x8 monome.
Coordinates use ~y=0~ at the top.

- Columns ~x=0..11~ correspond to pitch classes C through B.
- Top row ~y=0~ selects the root for future group-detune presses.
- Offset rows are ~y=1..7~.
- ~y=4~ means offset 0.
- Moving upward raises pitch: ~y=3~ is +1 step.
- Moving downward lowers pitch: ~y=5~ is -1 step.
- Columns ~x=13..15~ are group-detune controls.

Default group intervals, relative to the current root:

- ~x=13~ sets notes ~0, 2, 5, 7~
- ~x=14~ sets notes ~1, 3, 8, 10~
- ~x=15~ sets notes ~4, 6, 9, 11~

Group-detune presses write offsets into the main pitch-class offset
area. Later direct edits in the main offset area do not update the
group-detune columns.

Keyboard note-ons flash the corresponding pitch-class column at full
brightness for about 30 ms.

* Remappable un-12 monome

The ~edo-un12-*~ configs map the twelve piano pitch classes into an
arbitrary EDO. The monome grid size is inferred from serialosc's device
type when possible. Known sizes include 16x8 for monome 128 and 16x16
for monome 256.

The default layout uses:

- preimage row at ~y=0~, first 12 keys C through B
- EDO map below the preimage row
- undo button at the bottom-right key

Each EDO-map key represents:

#+begin_example
step = x_step*x + y_step*y mod edo
#+end_example

The lit EDO steps are the current image of the twelve piano pitch
classes. Initially they are spaced as evenly as possible. For 31-EDO:

#+begin_example
0, 3, 5, 8, 10, 13, 16, 18, 21, 23, 26, 28
#+end_example

For 58-EDO:

#+begin_example
0, 5, 10, 15, 19, 24, 29, 34, 39, 44, 48, 53
#+end_example

LED priorities:

- sounding pitches are steady on
- current images of C, F, and G flash at full brightness
- other current image pitches are steady dim

In the ~loose~ idiom, tapping a lit pitch makes its 12-EDO/EDO pair
loose. If at least one neighboring lit pitch is loose, tapping a dark
pitch moves a loose neighbor to that dark pitch and fixes it again.
If both neighbors are loose, the nearer one moves; ties pick the higher
neighbor.

In the ~snap~ idiom, tapping a dark pitch moves the nearest current
image to that pitch. Distance is measured in the EDO ring, not in the
2D monome layout. In a tie, the higher image snaps down.

The runtime tracks signed lift for each pitch class. For example, in
31-EDO, moving C from step 0 to step 30 means -1, not +30, so outgoing
MIDI moves down by one EDO step rather than jumping around the octave
ring.

* Monome EDO MIDI

~monome-edo-midi~ uses the same grid/chord model as the sawwave
runtime, but sends MIDI note events instead of rendering audio.

Cell ~(x,y)~ maps to absolute EDO step:

#+begin_example
step = x_step*x + y_step*y
#+end_example

MIDI output uses:

#+begin_example
channel = min_channel + step div EDO
note    = min_note + step mod EDO
#+end_example

The default virtual output port is:

#+begin_example
monome_edo_midi-out:out
#+end_example

* Monome EDO sawwave and chord storage

~monome-edo-sawwave~ renders audio directly with cpal and uses the
same chord storage UI as the MIDI grid runtime.

Default chord controls:

#+begin_example
              x=0     x=1     x=2     x=3     x=4 ... x=15
           +-------+-------+-------+-------+----- ... -----+
    y=14   | wipe  |accrete| emit- | set-  |   (EDO grid)  |
           |       |  -on  |  is-  | accr- |               |
           |       |       |toggle | target|               |
           +-------+-------+-------+-------+----- ... -----+
    y=15   |silence|chord 1|chord 2|chord 3| chord 4 ... 15|
           +-------+-------+-------+-------+----- ... -----+
#+end_example

Concepts:

- At most one chord is emitting; its button is bright.
- Exactly one chord is the accretion target; its button is dim unless
  it is also emitting.
- The emitting chord and target are independent.
- Chord 0 is silence and cannot be the accretion target.

Top-row controls:

| key | kind | behavior |
|-----+------+----------|
| wipe | fire | empty the accretion target; if it is emitting, ramp voices to silence |
| accrete-on | toggle | add EDO presses to the target; toggling on snapshots held keys |
| emit-is-toggle | toggle | on means chord buttons toggle; off means chord buttons are nursed |
| set-accretion-target | fire | press, then press a chord button to choose the target |

In toggle mode, pressing a chord switches the emitter to it; pressing
the current emitter toggles it off. In nursed mode, held chord buttons
form a stack: press B while holding A and B emits; release B and A
resumes.

If a pressed key's pitch is in the currently-emitting chord, releasing
that key can transform the fingered voice into an accreted sustained
voice. This only happens for the last alive origin voice for that pitch.

* Monome and serialosc operations

The serialosc detector listens on UDP port 12002. Send:

#+begin_example
/serialosc/list s <replyHost> i <replyPort>
#+end_example

It replies with one ~/serialosc/device~ message per connected device:

#+begin_example
/serialosc/device s <id> s <type> i <devicePort>
#+end_example

To receive key events and send LEDs, register with the device port:

| send | meaning |
|------+---------|
| ~/sys/host s "127.0.0.1"~ | event destination host |
| ~/sys/port i 9000~ | event destination port |
| ~/sys/prefix s "/mygridname"~ | OSC prefix for this client |

Then the device sends:

#+begin_example
/<prefix>/grid/key i x i y i s
#+end_example

where ~s=1~ is press and ~s=0~ is release.

LED commands include:

#+begin_example
/<prefix>/grid/led/set i x i y i s
/<prefix>/grid/led/all i s
/<prefix>/grid/led/level/set i x i y i level
#+end_example

The prefix is important: commands whose address does not begin with
the device's current prefix are silently ignored.

** Ghost tty devices

If serialosc reports several ports for the same device id, only the
newest may correspond to the physical grid. Stale serialosc-device
processes can be left behind after FTDI USB re-enumeration.

Symptoms:

- serialosc reports multiple ~/serialosc/device~ replies for one id
- LEDs may work on one port while key events never arrive
- host logs may show ~libmonome: error in write: Input/output error~

Host-side fix:

#+begin_src sh
systemctl --user restart serialoscd
# unplug the monome, wait about 3 seconds, replug
#+end_src

After restart, there should be one serialosc-device child on one
~/dev/ttyUSBN~.

* Brightness

On Jeff's grid, the 0-15 level API appears to have roughly four
visible brightness buckets rather than sixteen. For UI design, use a
small set such as 0, 4, 8, and 15 instead of depending on fine-grained
brightness differences.

To re-test:

#+begin_src sh
bash code/rust/demos-and-explorations/monome/12-brightness-test.sh
bash code/rust/demos-and-explorations/monome/12-brightness-test.sh 8
#+end_src

* Latency

One sawwave session showed roughly 100 ms between button press and
audible sound, while LEDs responded immediately. PipeWire buffer
defaults are the most likely cause; Docker without realtime scheduling
may also contribute.

Mitigations:

- request a smaller cpal buffer
- run on the host rather than in Docker
- grant the container ~CAP_SYS_NICE~ and ~--ulimit rtprio=99~
- consider JACK bindings via PipeWire's JACK interface

* MIDI connection recipes

The old helper scripts all used ~code/rust/connect-midi-lib.sh~.
Equivalent operations:

For piano input configs:

#+begin_src sh
connect_keyboard_to_alsa_client "edo12n_piano" "edo12n_piano-in"
connect_keyboard_to_alsa_client "edo12n_piano_monome" "edo12n_piano_monome-in"
connect_keyboard_to_alsa_client "edo_un12_piano_monome" "edo_un12_piano_monome-in"
#+end_src

For Reaper MIDI output:

#+begin_src sh
connect_pipewire_midi \
  "Midi-Bridge:edo12n_piano-out:(capture_0) out" \
  "REAPER:MIDI Input 1" \
  "edo12n_piano-out -> REAPER MIDI Input 1"

connect_pipewire_midi \
  "Midi-Bridge:edo12n_piano_monome-out:(capture_0) out" \
  "REAPER:MIDI Input 1" \
  "edo12n_piano_monome-out -> REAPER MIDI Input 1"

connect_pipewire_midi \
  "Midi-Bridge:edo_un12_piano_monome-out:(capture_0) out" \
  "REAPER:MIDI Input 1" \
  "edo_un12_piano_monome-out -> REAPER MIDI Input 1"

connect_pipewire_midi \
  "Midi-Bridge:monome_edo_midi-out:(capture_0) out" \
  "REAPER:MIDI Input 1" \
  "monome_edo_midi-out -> REAPER MIDI Input 1"
#+end_src

For Reaper audio output, choose available PipeWire playback sink ports
for left and right channels and connect:

#+begin_src sh
pw-link "REAPER:out1" "$left_sink"
pw-link "REAPER:out2" "$right_sink"
#+end_src
