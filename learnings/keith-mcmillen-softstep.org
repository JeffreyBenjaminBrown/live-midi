#+title: Keith McMillen SoftStep (KMSS): reading it, its protocol, velocity, and the drumkit
#+date: 2026-06-30

The complete field report on getting a SoftStep foot controller talking to this
container: how to read it, how to *send* to it (the thing an earlier draft thought was
impossible), how to get *velocity* and reliable *two-foot* hits out of it, and how the
velocity drumkit runtime works and is tuned. (This absorbs the former
=kmss-research.org=; it is now the one document.)

* Bottom line (what works today)

- *Sending WORKS -- via ALSA rawmidi, not the sequencer.* =amidi -p hw:1,0,0= reaches
  the device's USB-MIDI IN; =aseqsend= (the ALSA *sequencer*) is silently ignored.
  This was the whole wall, and it is gone. The firmware query is answered and the
  standalone<->tether mode switch takes effect.
- *Firmware = build 91* (decoded from the query reply), *pre-bootloader, healthy.*
- *Reading works* (via seq =20:0= or rawmidi). In its current standalone programming
  the device sends only *Program Changes* -- pedal identity, *no velocity*.
- *Velocity + pad identity* come from *tether/hosted mode*, which streams each pad's 4
  pressure sensors as CC. The printed-label -> CC map is *measured* (below), and the
  =drumkit_runtime= now plays *velocity-sensitive*.
- *Two feet at once*: *100% reliable in tether* (measured 6/6); *standalone is lossy*
  (drops to one or zero Program Changes) -- that is the =concurrent-drums.org= problem,
  and tether fixes it.
- *Nothing here can brick the device*: only an interrupted firmware *flash* can, and we
  never flash. See [[*Bricking: the precise, reassuring truth]].

* The device, precisely

#+begin_example
USB:   1f38:000b   "KESUMO, LLC" / "SSCOM"   bcdDevice 0100   (Kesumo = KMI's sensor arm)
Firmware: build 91 (0x5B), version string "91", status "GG" = healthy.
          91 <= 94  ->  PRE-BOOTLOADER (no bootloader present).
ALSA:  client "SSCOM" (kernel, card 1). The client NUMBER (e.g. 20) is assigned at
       plug-in and is NOT stable -- match by the name substring "SSCOM", never 20:0.
       20:0 = "SSCOM MIDI 1" (Port 1, performance)   20:1 = "SSCOM MIDI 2" (Port 2)
Rawmidi: /dev/snd/midiC1D0 exists ->  amidi hw:1,0,0 (Port 1) and hw:1,0,1 (Port 2).
#+end_example

*=hw:1,0,0= (Port 1) is the control + data port*: it answers the firmware query,
accepts mode-switch SysEx, and streams the sensor data. =hw:1,0,1= is silent for us.
Reading may go through either the sequencer (=20:0=) or rawmidi; the sequencer
*read* path carries the tether stream fine. Only the sequencer *send* path is the one
that does not reach the device.

/Hardware-rev note:/ the USB PID =0x0b= says "SoftStep 2", while a field in the firmware
reply decoded as "SoftStep 1". This ambiguity only affects *X/Y* sensor labeling, not
pad id / pressure / velocity / concurrency, so it does not matter for drums.

* Two SoftSteps (2026-07-15): telling them apart, and reading both

There are now *two* SoftStep units, and -- usefully -- they *enumerate differently*, so
code can tell which is which. The physical layouts differ, and the synth needs to know
which board is which; the device identity is the hook.

#+begin_example
  unit        USB / by-id                              ALSA client   control+data port
  ----------  ---------------------------------------  ------------  ----------------------
  ORIGINAL    usb-KESUMO__LLC_SSCOM-00                 "SSCOM"       "SSCOM MIDI 1" (hw:C,0,0)
  NEWER       usb-KMI_Music__Inc._SoftStep_722-000079  "SoftStep"    "SoftStep Control Surface"
#+end_example

Three independent ways to distinguish them (use the port NAME, never the card number --
the card number is assigned at plug-in and moved: the original unit was =hw:1,...= when
alone and is =hw:3,...= with both plugged in):

1. *ALSA client / port name.* Original -> "SSCOM" (ports "SSCOM MIDI 1/2"). Newer ->
   "SoftStep" (ports "SoftStep Control Surface", "SoftStep TRS MIDI Out", "SoftStep CV
   Out" -- three cables, vs the original's two). The substrings "SSCOM" and "SoftStep"
   are mutually exclusive, so each matches exactly one unit.
2. =/dev/snd/by-id=: "KESUMO, LLC / SSCOM" vs "KMI Music, Inc. / SoftStep 722-000079"
   (the newer one even carries a per-unit serial).
3. *Firmware-query reply shape* (each answers a DIFFERENT query -- itself an ID signal):
   - ORIGINAL answers the *KMI proprietary* query (=f0 00 1b 48 7a ...=) with the long
     FW header (build 0x5B = 91, still healthy) and IGNORES the universal identity request.
   - NEWER answers the *universal identity request* (=F0 7E 7F 06 01 F7=) with
     =F0 7E 00 06 02 00 01 5F 0D 00 ...= (KMI mfr id =00 01 5F=, device family =0D 00=)
     and does NOT give the proprietary FW header. So it runs *newer firmware*.

*Both units accept the SAME tether/standalone SysEx* (=ss.py=) and, once tethered, stream
sensors as *Control Change ch0 with the SAME pad->CC map* -- pads 40..79, nav 80..83, the
measured table below. Verified 2026-07-15: sending =standalone_off + tether_on= to the
newer unit's =hw:C,0,0= makes it dump all sensors and then stream on-change, exactly like
the original (it emits a full zero-valued sensor frame on entering tether). And a guided
per-pad capture (=capture.py A= on the newer unit) *confirmed all ten pads map identically*
(1->44, 2->52, 3->60, 4->68, 5->76, 6->40, 7->48, 8->56, 9->64, 0->72) -- note faint bleed
into a physically-adjacent pad's nearest sensor when pressed on carpet, but the dominant
group is always the assumed base. So the existing decoder / CC map applies to both boards;
the only new work was reading *two* devices at once and tagging each hit with its board.

*For the Python tools:* =ss.list_softsteps()= discovers every unit's control port by name
and returns =kind= ("sscom"/"softstep"), =label=, and =port=; every =ss= op takes an
optional =port==. The meter (=meter/main.py=) reads both boards and =pedals.py= excludes
them. Nothing hardcodes =hw:1,0,0= anymore.

*For the Rust synth:* select the original with =select.name_contains = "SSCOM"= and the
newer with =select.name_contains = "SoftStep"=. CAVEAT: the newer unit's data port is
named "SoftStep Control Surface", NOT "...MIDI 1", so =softstep_meter=/=drumkit_runtime='s
=select_input_port= (which prefers a "MIDI 1" substring) needs to also prefer "Control
Surface" to bind the right port on the newer board. The current drumkit rig targets the
original ("SSCOM"); a rig for the newer board sets =name_contains = "SoftStep"=.

* Reading the device

** Connecting

Three ways in, easiest to most production-ready:

1. *Parse =aseqdump=* (what =echo.py= does): =stdbuf -oL aseqdump -p 20:0=, read lines,
   regex the event. Zero deps; fine for a monitor. (=aseqdump= ignores SIGTERM --
   SIGKILL it.)
2. *Python =python-rtmidi= / =mido=* -- clean callback API, but NOT installed here, so
   our Python tools shell out to =amidi= / =aseqdump= instead.
3. *Rust =midir=* -- the project's MIDI lib, and where this lives
   (=code/rust/midi_pulse/=). Open the input matching "SSCOM" (prefer "MIDI 1"),
   register a callback, match on the status nibble. midir reads via the sequencer, and
   the tether CC stream comes through it.

** Standalone Program-Change mode (what it sends now)

The device currently holds a *Program-Change bank-switcher* programming:

#+begin_example
  pedal labeled P (1..9, then 0) on preset K (display 0..12)
      -->  Program Change number = 10*K + P   on MIDI channel 1
#+end_example

So 13 presets x 10 pedals = *PC 0..129*. Decode preset-independently:
=pedal = program % 10= (so a bumped on-device preset never breaks the kit).

- *No velocity, pressure, aftertouch, X/Y, or notes* in *any* preset -- a Program
  Change physically can't carry velocity.
- The *4 nav arrows emit no MIDI*; they only scroll presets on the numeric display
  (which also echoes the last pedal pressed).
- *Contact bounce:* a hard stomp can emit the *same* PC twice within a few ms. Debounce
  *per pedal* (~15-50 ms) if you don't want double-triggers -- keep it per-pad so two
  *different* pedals struck together both still fire.

** Tether/hosted mode -- pad + velocity

In tether mode the device streams *every sensor* as *Control Change on channel 0*
(=0xB0=): CC number = sensor index, value 0..127 = reading. Each pad owns 4 consecutive
CCs =baseCC..baseCC+3=.

*The printed-label -> CC map (MEASURED on this device -- definitive):*

#+begin_example
  printed label:  1    2    3    4    5    6    7    8    9    0
  base CC:       44   52   60   68   76   40   48   56   64   72
  4 sensors:   44-47 52-55 60-63 68-71 76-79 40-43 48-51 56-59 64-67 72-75
#+end_example

(Internally key index = label-1, with "0" = index 9.) Other CCs in the stream:
*CC 80-83* = the nav pad's 4 sensors; *CC 86* = the *expression-pedal* jack. The idle
flicker you'd see at rest (CC 86 ~= 126/127 or 0) is just that analog jack floating with
nothing plugged in -- not a pad, not a heartbeat, not a signal.

*Pressure* from the four sensor values:
- *max-of-4* (the editor's default) *saturates* -- measured soft = 74/106 but medium =
  116/117 and hard = 118/117, because one corner pegs at 127 on any firm press. Medium
  and hard become indistinguishable.
- *sum-of-4* (0..508) has 4x the headroom and separates hits far better. *Use sum-of-4.*

*Velocity* (the device has none of its own -- it's ours to derive):
- *onset* = pressure crossing an on-threshold from below; *release* = falling below a
  lower off-threshold (hysteresis avoids chatter).
- *velocity* = the *peak sum-of-4 within a short attack window* after onset, scaled to
  1..127. See [[*Drumkit velocity (tether runtime): how it works + the tuning knobs]] for
  the crucial timing fact (the device refreshes only ~every 10 ms) and the knobs.

* Two feet at once

The old reasoning -- "MIDI is serial, both presses are sent, nothing is dropped" -- is
true *on the wire*, but the *standalone preset* itself is effectively monophonic and
collapses a near-coincident two-pad press into a single Program Change. Measured:

| mode               | two-pad stomp result (from capture)                                    |
|--------------------+------------------------------------------------------------------------|
| *tether* (hosted)  | *both* pads stream, every time (6/6). Continuous per-sensor scan, so    |
|                    | there is no discrete note for one foot to steal. 100% reliable.         |
| *standalone* (PC)  | unreliable: some stomps gave *two* PCs, others *one* or *zero*. This is  |
|                    | the =concurrent-drums.org= loss -- it lives in the standalone preset.    |

Conclusion: *tether mode is the fix for concurrency* (and it gives velocity too -- one
solution to both problems).

* Sending to the device (the breakthrough)

An earlier draft concluded "we can't send to the device." That was tested only through
the ALSA *sequencer* (=aseqsend=), which the SoftStep silently ignores. The ALSA
*rawmidi* path works:

#+begin_src sh
  amidi -p hw:1,0,0 -S "<hex sysex>"        # reaches the device's USB-MIDI IN
#+end_src

Proof, all reproducible on the device: the *firmware query* gets a reply (decoded to
build 91); *standalone_off + tether_on* makes the device emit Control Change data
(which standalone PC mode never does); *tether_off + standalone_on* restores it and the
query still answers (healthy). The =amidi -d= reader also transiently holds the port, so
a following send can get =EBUSY= -- retry on "busy" (our =ss.py= does).

*Why the sequencer path failed* (now moot, kept as a lesson): =aseqsend= demonstrably
delivers MIDI (a Note loops back through Midi Through =14:0=), so the send *mechanism*
was fine -- but the device did not honor mode/backlight/query SysEx over the sequencer
on either port. The rawmidi endpoint does. (The editor's =connected= handshake is an
*editor-side* guard only; the firmware honors =tether_on= with no prior handshake --
matching that a bare mode switch works.)

* Bricking: the precise, reassuring truth

The only thing that bricks a SoftStep is an *interrupted firmware FLASH* on
*pre-bootloader* firmware -- KMI: /"Firmware 94 and earlier did NOT have a bootloader...
a firmware update carries a small risk that if the update is interrupted, your SoftStep
could become bricked."/ This unit is pre-bootloader (build 91), so that caveat applies
*to flashing* -- which we never do. Everything we do is non-flash and reversible:

| operation                         | flashes firmware? | worst case                          | brick risk |
|-----------------------------------+-------------------+-------------------------------------+------------|
| firmware identity *query*         | no (read request) | no reply                            | *none*     |
| standalone<->tether *mode switch* | no (runtime mode) | wrong mode -> resend restore        | *none* (proven reversible) |
| *backlight* SysEx                 | no (LED toggle)   | nothing                             | *none*     |
| upload a *preset/scene*           | no (preset memory)| bad preset -> re-upload / pick other | *low, recoverable* |
| firmware *flash*                  | *YES*             | interrupted on fw <=94 -> brick     | the one risk |

KMI: /"If your SoftStep still turns on, flashes LEDs, and is responsive to key presses,
it is not bricked."/ (Ours does all three and still answers the query.) Even a true
brick they fix *free* by mail-in. *The single thing to avoid:* if KMI's editor ever
offers to update/reload firmware, click *No*. We don't use the editor, so it won't come
up -- and you do *not* need a Mac: we read richer data out of the firmware already on the
device, we don't change it.

* The tools (=code/python/softstep/=)

No Python MIDI libraries needed -- everything shells out to =amidi= / =aseqdump=
(alsa-utils). The mode-changing tools *restore standalone mode on exit*, including on
Ctrl-C.

- *New, rawmidi-based (use these):*
  - =ss.py= -- shared helpers: the working rawmidi port, control-SysEx bytes, and
    =enter_tether()= / =restore_standalone()= / =query()=. Run directly to print the
    firmware reply.
  - =probe.py= -- autonomous reachability proof (no foot): fires the query and prints
    the reply. Good link check.
  - =capture.py= -- self-paced guided capture (tether + two-foot + standalone PC),
    logs to =captures/session-*.log=.
  - =meter/main.py= -- live *DUAL*-board meter. Reads *every* connected SoftStep at once;
    the live display shows the *last two pads pressed* (across both boards), each as its
    *4 individual sensors + their sum*, tagged with which board/pad. On a hit it prints
    the velocity and plays the configured audition sample (=audition-sample= in
    =meter/config.toml=). Two logs under =meter/logs/=: a deep-dive *CSV*
    (=csv/session-<stamp>.csv=, one row per sensor frame + per fired hit, both boards) and
    the per-pad *.org* event groups (=<device>/pad-<label>/<N>.org=, raw sum trace + a
    re-derived hit interpretation). Tunables in =meter/config.toml= (reload with =r=). For
    calibrating touch and diagnosing missed/double hits.
- *Expression pedals (a different device -- DOREMiDi MPC-20 + M-Audio EX-P):*
  =code/python/pedals/pedals.py= -- live MIDI monitor for expression-pedal CC: per
  =(channel, CC)= it shows value + 0..127 sweep bar + *min/max seen*, so a pedal that only
  reaches 35..127 is visible at a glance. CSV to =pedals/logs/=. See
  =code/python/pedals/README.org= for the EX-P range fix (MIN knob + polarity switch) and
  the MPC-20 (Pedal Config Tool, per-input channel/CC, CC 21 default).
- *Older, sequencer-based (echo still handy; the senders used the dead seq path):*
  =echo.py= (human-readable =aseqdump= monitor -- still useful), =backlight_blink.py=
  and =ssmode.py= (sent control SysEx via =aseqsend=, so they had *no effect*; kept only
  as a protocol record -- port them to =amidi= if needed).

*Batched capture:* run =python3 code/python/softstep/capture.py=, follow the self-paced
prompts (it waits for Enter, never times you), and it writes one log to read back.

* Drumkit velocity (tether runtime): how it works + the tuning knobs

The =drumkit_runtime= plays *velocity-sensitive*: on start it switches the device into
tether mode (over rawmidi via =amidi=), reads the CC sensor stream through midir, FIRES a
voice the instant a pad's sum crosses the onset threshold (so even a one-sample tap
counts), then RAMPS that voice's gain up if a higher peak arrives during the attack watch
window -- all through the polyphonic =VoicePool= -- and *restores standalone mode on exit*
(Enter, error, or Ctrl-C/SIGTERM).

** The one empirical fact that drives everything
The device refreshes its sensors only *~every 10 ms* (~100 Hz scan -- measured from
timestamped captures; it is fixed in firmware, not tunable). A deliberate strike's
pressure peaks on the *2nd refresh* (~10-11 ms after the hit is first seen) on a
*hard floor*; on a springy/mushy surface (carpet) the peak lags 20 ms or more.
Consequences:
- The peak isn't known until ~2 refreshes in. Rather than *wait* to fire (which delayed
  every hit and dropped one-sample taps), the runtime FIRES on onset and then RAMPS the
  voice up to the true peak as it arrives -- so =ATTACK= is a *watch-and-adjust* window, not
  a "wait this long before firing" delay. Keep it >= ~2 refreshes (~14 ms) so a hard hit's
  late peak still lands inside it; shrinking it just caps how loud a late peak can push the
  voice (it no longer adds latency).
- Polling the stream faster than ~10 ms captures nothing new; it only trims onset-fire
  latency and how promptly a mid-window loudness revise reaches the voice (poll is 1 ms).
- *Surface matters.* A hard floor sharpens the attack (peak ~10 ms, consistent); a soft
  surface slows and scatters it. Re-check =ATTACK= if you change playing surface.

** The knobs
The detection & velocity knobs are all *rig* now: they live in the shared
=code/rust/rigs/softstep.toml= (loaded by =drumkit_runtime=), not as =decode.rs=
consts. The poll interval is the one exception (=drumkit_runtime/mod.rs=). The Python
meter =code/python/softstep/meter/= mirrors them in its own =rig.toml= (=on-sum=,
=attack-ms=, =debounce-ms=, ...) so what you audition matches the kit. Symptom -> fix:

| knob                | default | what it does                                                        | symptom -> fix                                                                                          |
|---------------------+---------+---------------------------------------------------------------------+--------------------------------------------------------------------------------------------------------|
| =ATTACK=            | 14 ms   | after firing on onset, how long we keep watching to ramp the voice up to a later, higher peak | hard hit stays *weak* (its peak lands past the window) -> raise 1-2 ms; fire is immediate now, so it adds no latency |
| =gain_db_range= (softstep.toml) | 20 dB | loudness spread from softest (pressure 0) to hardest (pressure 1) hit | dynamics feel *flat* -> raise (e.g. 30); soft hits *vanish* / too extreme -> lower (e.g. 12)              |
| =pressure_full_scale= (softstep.toml) | 460 | pad pressure (sum of its 4 sensors, 0..508) that maps to full pressure 1.0 | *everything maxes out*, no headroom -> raise toward 508; *can't reach full* even hitting hard -> lower    |
| =on_sum= / =off_sum= | 20 / 20 | onset / release thresholds on the pad's sum-of-4 (hysteresis)      | *double/false* triggers -> raise =on_sum=; a pad *won't retrigger (stuck)* -> lower =off_sum=             |
| poll interval       | 1 ms    | how often the fire-timer checks for matured hits                     | rarely needs changing; the ~10 ms device scan dominates                                                |
| =debounce_ms= (softstep.toml) | 100 ms | min gap between two hits on the SAME pad, *in addition to* a release below =off_sum= | *machine-gunning / bounce on one pad* -> raise; *fast rolls cut off* -> lower (0 = release-only)         |
| =silence_to_zero_ms= (softstep.toml) | 25 ms | a sensor with no CC for this long reads 0 (de-stick) -- the on-change stream leaves a physically stuck sensor's last value lingering, pinning a pad Held | *a pad won't retrigger after a stuck sensor* -> lower; *held/sustained presses cut out* -> raise (0 = off) |

Pressure = the *peak of sum-of-4* over the =ATTACK= window, over =pressure_full_scale= (a
continuous 0.0..1.0 -- no 0..127 quantization step), then converted to a gain spread over
=gain_db_range=. (Loudness is ~logarithmic, so pressure is spread across dB rather than
scaling amplitude linearly -- linear would put full pressure ~42 dB above a light press,
far too much.) After changing any knob,
rebuild: =pw-jack cargo run --bin midi_pulse -- kmss-drumkit=. The pure decoder has unit
tests (=cargo test --bin midi_pulse drumkit=).

* Alternative: a "notes" preset (for the record)

Because sending works, each pad could instead send a *Note On* (standard, trivially
polyphonic). The SoftStep even ships a factory "Notes" preset (pads -> notes 60-69),
possibly selectable via the nav arrows or a Program Change (=amidi -p hw:1,0,0 -S
"C0 02"=). But two catches make it inferior to tether for drums: on-device note velocity
is a *fixed constant* (no attack dynamics), and the factory default is *single-key
lockout* (one pad at a time), so reliable two-foot play needs an "All Keys" settings
upload. *Tether is the path for velocity + concurrency*; the notes preset is only worth
it for dead-simple fixed-velocity note identity.

* The tether/hosted protocol (reverse-engineered, from the editor source)

KMI open-sourced their editor: *github.com/Muse-Kinetics/softstep_editor* (C++, MPL-2.0,
default branch =main=). Key facts, verbatim from the source:

- *Tethered data = Control Change ch0* (=standalone/advanced/hosted/midiparse.cpp=,
  "Used only for SSCOM Port 1 data"): =if(data[0]==176) emit signalUpdateSensor(cc,val)=.
- *pedal -> base CC* (=hosted/datacooker.cpp= =keySensorBaseCcMap=): the table above; a
  pad's 4 sensors are =baseCC..baseCC+3=. On SS1 the offsets are corners NW,NE,SW,SE; on
  SS2/3 they are edges N,E,W,S (only matters for X/Y).
- *pressure* = =max-of-4= (default, =sensorResponse=0=) or =avg-of-4= (=1=), each value
  first x=globalGain= (default 1.0) and clamped to 127; hysteresis =onThresh=10=,
  =offThresh=5=. There is *no velocity curve* in the firmware -- derive it from the attack.
- *X/Y* from sensor-mass differences (=xLoc=, =yLoc= in datacooker.cpp).

** The mode-switch SysEx (verbatim, mirrored in =ss.py=)
SysEx start =F0=, stop =F7=, KMI id =00 01 5F=, magic =7A=. Hosted-enable is the editor's
=slotHostedOnOff(true)= (order matters; firmware "requires delay between messages" --
send with a ~120-150 ms gap). Bytes (43 each):

#+begin_example
  standalone_off            f000015f7a01 00*10 00010009000b2b3a 0010 03 00 00000000000000 5007 000000 02 f7
  scenechange_on_persist    f000015f7a01 00*10 00010009000b2b3a 0010 08 01 01000000000000 7b69 000000 02 f7
  nav_standalone_on_persist f000015f7a01 00*10 00010009000b2b3a 0010 09 01 01000000000000 3c3a 000000 06 f7
  tether_on                 f000015f7a01 00*10 00010009000b2b3a 0010 04 01 00000000000000 2f7e 000000 02 f7
  --- restore (standalone) ---
  tether_off                f000015f7a01 00*10 00010009000b2b3a 0010 04 00 00000000000000 171f 000000 00 f7
  standalone_on             f000015f7a01 00*10 00010009000b2b3a 0010 03 01 00000000000000 6866 000000 00 f7
#+end_example

(=00*10= = ten 0x00 bytes; the two bytes before the trailing pad are a per-message CRC
-- send them verbatim.) The *minimal* pair =standalone_off + tether_on= (and =tether_off
+ standalone_on= to restore) is enough to start/stop the CC stream; the two =_persist=
messages just re-assert scene/nav settings. The firmware query uses a *different* id
(=00 1B 48 7A=) -- kept "wrong for old firmware" on purpose so old units still reply.

* The firmware identity reply (raw + decode)

Reproducible reply to the KMI query on =hw:1,0,0=:

#+begin_example
F0 00 1B 48 7A 01  [~50x 00]
01 00 05 00 13 4D 62 00 00 50 00 5B 21 4F 08 41 08 47 47 00 00 39 31 ...
01 00 0D 00 08 47 19 00 20 ...  F7
#+end_example

Decoded via the editor's own parser (=sysexcomposition/query.c= + =syxrx.{c,h}=, after
undoing the 8->7-byte SysEx packing): packet type 5 = FW_HEADER whose =buildnum= = 0x5B =
*91* and whose versionString = ASCII "91" (two fields agree); =fw_status= = "GG" = error
0 = *healthy*. Packet type 13 = MISC_INFO, =hardware_type= = 0. Build 91 <= 94, so
*pre-bootloader* (matches the legacy "SSCOM" enumeration).

* MIDI pitfalls learned (save yourself the time)

- =aseqdump= *ignores SIGTERM* -- =timeout 4s aseqdump ...= hangs; use =timeout -s KILL=
  or =kill -9=. Its banner is fully-buffered stdout, so SIGKILL loses it; use =stdbuf -oL=
  when capturing to a file.
- =amidi= *block-buffers stdout when piped* -- wrap in =stdbuf -oL amidi ...= or live
  readings never reach the log until a big buffer fills.
- *Passive listening shows nothing* -- the device only emits when you step on it (and in
  tether mode, only *on change*; at rest just the pedal CC 86 flickers). An empty capture
  means "nobody pressed anything," not "broken."
- =aseqsend -s= takes a *filename*, not a hex string (despite the usage text). Write the
  bytes to a =.syx= first. =aseqsend -v= confirms "Sent : N bytes".
- *Send via rawmidi, not the sequencer* -- the device honors =amidi= (=hw:1,0,0=) and
  ignores =aseqsend=. (The sequencer's send mechanism is fine -- it loops back through
  Midi Through -- the *device* just doesn't honor its control SysEx.)
