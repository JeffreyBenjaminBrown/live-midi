#+TITLE: monome/ — grid synth + hard-won ops notes

This directory contains a tiny Rust synth driven by a monome grid,
plus the scripts and notes from resurrecting Jeff's monome on NixOS
in April 2026.

* Architecture

#+begin_example
  monome USB ─── ftdi_sio ──┐  host NixOS
                            │
                            ▼
          /dev/ttyUSBN  (owned root:dialout)
                            │
                            ▼
              serialoscd  (user systemd service)
              detector @ :12002
              device    @ :PORT   ← assigned per connect; changes!
                            ▲
                            │  OSC/UDP
                            │
    ┌───────────────────────┴────────────────────────┐
    │   docker container (--network host, so        │
    │   localhost in container == localhost on host) │
    │                                                 │
    │    grid_synth  (this repo)                      │
    │      - listens on :9000 for grid events         │
    │      - cpal → /run/user/1000/pipewire-0         │
    │        (socket mounted from host)               │
    │      - /dev/snd bind-mounted; audio group added │
    └─────────────────────────────────────────────────┘
#+end_example

The container is started by =../docker.sh=. Relevant flags:
=--network host= (localhost passthrough), the =pipewire-0= bind
mount, =/dev/snd= device, and =--group-add audio=.

* Running grid_synth

Inside the container:

#+begin_src bash
cd /home/ubuntu/monome
bash ./11-grid-synth.sh [FUND [EDO [X_STEP [Y_STEP]]]]
#+end_src

Args default to =220 46 9 1= — i.e. =(0,0) = 220 Hz=, pitch rises
9/46 of an octave per x step and 1/46 of an octave per y step. All
four args are =f64=, so fractional EDOs work.

* Chord storage (twenty special keys, two control windows)

The bottom two rows of the grid are no longer EDO; they're a small
UI for storing and replaying *chords* — sets of accreted pitches.
Two windows obscure the EDO grid beneath them:

#+begin_example
              x=0     x=1     x=2     x=3     x=4 ... x=15
           +-------+-------+-------+-------+----- ... -----+
    y=14   | wipe  |accrete| emit- | set-  |   (EDO grid)  |
           |       |  -on  |  is-  | accr- |               |
           |       |       |toggle | target|               |
           +-------+-------+-------+-------+----- ... -----+
    y=15   |silence|chord 1|chord 2|chord 3| chord 4 ... 15|
           +-------+-------+-------+-------+----- ... -----+
            ^^^^^^^^^^^^^^ controls-top (4 cells) ^^^^^^^^^^
                              ^^^^^^^^^^^^^^^^^^^ controls-bottom (16 cells) ^^^^^^^^
#+end_example

** Concepts

There are *15 chord slots* (chord 1 through chord 15), plus a
"silence" slot that's always empty. At any moment:

  - At most one chord is *emitting*. Its accreted pitches sound;
    its button is fully bright.
  - Exactly one chord is the *accretion target*. New presses (while
    =accrete-on= is on) go into its slot, and =wipe= empties it.
    The target's button is dimly lit (unless it's also the
    emitter, in which case full bright wins).
  - The emitting chord and the accretion target are *independent*.
    You can sustain chord A while building up chord B.
  - Silence cannot be the accretion target. Pressing it just
    emits-nothing — useful as a "stop the current chord" key.

** Top-row controls (y=14)

| Key                       | Kind   | What it does                                            |
|---------------------------+--------+---------------------------------------------------------|
| =wipe=                    | Fire   | Empties the *accretion target* slot. If the target is also the emitting chord, its voices ramp to silence. |
| =accrete-on=              | Toggle | While on, every EDO press adds its pitch to the *accretion target's* slot. Toggling on also snapshots whatever's currently held. |
| =emit-is-toggle=          | Toggle | Picks the chord-button mode globally. On (default) ⇒ chord buttons are Toggle (press to flip). Off ⇒ chord buttons are Nursed (emit only while held; releases pop a stack). |
| =set-accretion-target=    | Fire   | Press, then press a chord button — that chord becomes the new target. The button flashes while waiting for your selection. Press it again, or any non-chord-button, to cancel. |

** Bottom-row chord buttons (y=15)

| Cell           | What it is                                                     |
|----------------+----------------------------------------------------------------|
| (0, 15)        | =silence= — a chord whose slot is always empty.                |
| (N, 15) N=1-15 | Chord N. Each holds its own pitch set.                         |

In *Toggle mode* (the default), pressing a chord button switches
the emitter to it; pressing the currently-emitting chord toggles it
off. Only one chord emits at a time.

In *Nursed mode*, the chord buttons form a stack: hold A, then
press B → B emits, A is buried; release B → A resumes emitting;
release A → silence. Any number of buried chords can be stacked.

** The sustain-pedal rule

If you press a key whose pitch is in the currently-emitting
chord's slot, then release it, the voice doesn't go silent: it
ramps from full down to the half-volume accretion level and keeps
ringing as part of the chord. (Specifically: this fires only when
you're the *last alive originVoice* for that pitch in that chord —
multiple enharmonic keys hold the pitch alive together until the
last is released.)

** Brightness

Each chord button has three resting states (off / dim / bright):

  - *Bright* if it's the emitting chord.
  - *Dim* if it's the accretion target (and not silence).
  - *Off* otherwise.

If a chord is both the target *and* the emitter, bright wins.

The =set-accretion-target= cell sits at *Dim* normally and flashes
between *Bright* and *Off* every 150 ms while in selection mode.
See the "Coding the monome" section below for why we use only four
distinct brightness levels.

* The monome OSC protocol in one page

All communication is OSC over UDP. The monome (via serialoscd) both
receives commands and sends grid events.

** Discovery

The ``detector'' listens on UDP :12002. Send it:

  =/serialosc/list s <replyHost> i <replyPort>=

It replies, to replyHost:replyPort, with one =/serialosc/device= per
connected device:

  =/serialosc/device s <id> s <type> i <devicePort>=

=devicePort= is where commands for that device go. It is NOT stable:
a new one is picked every time serialoscd notices the device, which
happens on restart or on USB re-enumeration.

** Per-device registration

To receive key events and send LED commands, talk to =devicePort=:

| Send                                | Meaning                               |
|-------------------------------------+---------------------------------------|
| =/sys/host   s "127.0.0.1"=         | Where to forward events back to you.  |
| =/sys/port   i 9000=                | Which UDP port on that host.          |
| =/sys/prefix s "/mygridname"=       | Filter: only commands/events w/ prefix.|

After that, the device sends key events to =127.0.0.1:9000=:

  =/mygridname/grid/key i x i y i s=    (s=1 press, s=0 release)

And accepts LED commands addressed with the same prefix:

  =/mygridname/grid/led/set i x i y i s=
  =/mygridname/grid/led/all i s=

The ``prefix'' is a label you assign to the device. Commands whose
address doesn't begin with the device's current prefix are silently
dropped — if your presses produce no sound and your LEDs don't
change, check the prefix first.

* Coding the monome

** Brightness: only ~4 distinct levels, despite the 0-15 API

The standard monome OSC protocol exposes per-cell brightness via
=/<prefix>/grid/led/level/set i x i y i level=, with =level= in
[0, 15]. We measured this on Jeff's grid using
=12-brightness-test.sh= (paints a row with ascending brightness
0..15) and observed *roughly four* distinct visual levels across
that range, not sixteen. So the device — whether by hardware,
firmware, or serialosc's translation — buckets the API value
into a much coarser scale.

Practical implication: when designing UI that uses brightness for
information density (e.g. dim/mid/bright/full to encode held vs.
sustained vs. emphasised states), pick four roughly equally-spaced
=level= values, not sixteen. Something like 1, 5, 10, 15 is a
reasonable starting set.

To re-test on this device, or to characterise a different one:

#+begin_src bash
bash ./12-brightness-test.sh        # paint row 0 with 0..15
bash ./12-brightness-test.sh 8      # row 8
#+end_src

(Best with =grid_synth= not running, so live presses don't
overwrite the test row with binary on/off LEDs.)

* Known gotcha: ghost /dev/ttyUSBN devices

On one session we observed =systemctl --user status serialoscd=
showing THREE =serialosc-devic= children, one each for
=/dev/ttyUSB{0,1,2}=, all reporting themselves as the same device id
=m0000102= on three different OSC ports (15326, 15997, 16104). Only
the latest tty corresponded to the physically connected grid; the
other two logged =libmonome: error in write: Input/output error=.

Cause: the FTDI USB-serial chip got re-enumerated while serialoscd
was already watching =/dev/ttyUSB0=. The kernel gave the new
enumeration =/dev/ttyUSB1=, then again as =/dev/ttyUSB2=.
serialoscd's detector spawned a fresh =serialosc-device= process for
each new tty but never cleaned up the dead ones.

Symptom inside this project: a client registers via
=/serialosc/list= and gets back one of the ports (say 15326). Key
events never arrive because that port's =serialosc-device= is the
stale one; only the newest port actually reaches the grid.

Fix:

#+begin_src bash
# on the host
systemctl --user restart serialoscd
# unplug the monome, wait ~3 s, replug
#+end_src

After restart =status= should show exactly ONE =serialosc-devic=
child on a single =/dev/ttyUSBN=.

** grid_synth's defense

=grid_synth= watches for =/serialosc/device= messages even after
startup. Any such message with a port different from our current
device port triggers a fresh =register()= to the new port. This
makes the synth survive serialoscd restarts while running, though
it doesn't help with pre-existing stale devices.

* Known issue: latency

Approximately 100 ms between button press and audible sound, even
though the LED response is immediate. Baseline audio buffer size
from PipeWire defaults is the most likely cause (see =grid_synth=
audio stream setup). Being in Docker without RT scheduling may
contribute but is not expected to be the dominant factor.

Mitigations that may help (in order):
- Request a small cpal buffer (=BufferSize::Fixed(256)=).
- Run grid_synth on the host rather than in the container.
- Grant the container =CAP_SYS_NICE= / =--ulimit rtprio=99= so the
  audio thread can be bumped to RT via =audio_thread_priority=.
- Switch from cpal to the JACK client bindings, using PipeWire's
  JACK interface directly.
